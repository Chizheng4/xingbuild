# xingbuild Visual System v1

## 1. 文档状态

- 版本：Visual System v1
- 状态：已实施的全站设计基线；由后续稳定修订持续校准
- 日期：2026-07-25
- 设计责任：网站产品与视觉分析 task
- 实施责任：Engineering 网站迭代 task
- 适用对象：xingbuild 全站页面、内容投影、组件和响应式表现

Visual System v1 是视觉决策的事实源。它不改变网站已经确认的品牌、内容对象和信息架构，而是把暖色编辑型方向变成可以复用、验证和演进的工程合同。

## 2. 系统目标

xingbuild 的视觉系统需要同时服务三件事：

1. 让读者快速理解作者持续观察和构建什么；
2. 让中文长文、短观察、作品与职业证据都容易阅读；
3. 让后续迭代通过语义 token 和稳定组件完成，而不是反复调整散落的 CSS 数值。

根本关系是：

```text
品牌语义
    ↓
视觉 token
    ↓
排版与空间规则
    ↓
页面和内容组件
    ↓
响应式投影
    ↓
真实阅读与验证反馈
```

## 3. 参考边界

### 3.1 从 Maggie Appleton 学习的机制

- 用一个强标题建立作者长期主题；
- 标题、说明、元数据、正文形成清楚的字体角色；
- 使用流体字号和空间尺度，而不是只在断点处跳变；
- 保持同一视觉语言，手机端重新排布而不是整体换风格；
- 正文以受控行宽、充足行高和大段落间距降低阅读负担；
- 内容组件由稳定对象驱动，页面只是不同投影。

### 3.2 不复制

- Canela 字体本身及其授权资产；
- 花园、生长阶段和植物图形；
- 手绘插画和装饰性边注；
- 多种内容类型和复杂筛选；
- 自动跟随系统深色模式；
- 英文内容的超大字号比例直接套用到中文。

## 4. 品牌视觉原则

### 4.1 直接

信息层级由文字本身、尺度、对齐和留白建立，不依赖装饰性卡片、阴影和边框。

### 4.2 温暖但精确

暖白和编辑型衬线表达长期阅读；墨色、赭色、编号和业务架构线表达系统性与工程精度。

### 4.3 内容优先

视觉不能掩盖作品状态、证据边界、发布日期和内容成熟度。图形只在帮助理解对象、关系、顺序或反馈时出现。

### 4.4 同一品牌，不同密度

桌面更疏、更具编辑感；手机更紧凑、更直接。但两端必须共享同一颜色角色、字体角色和组件语义。

### 4.5 固定浅色基线

xingbuild 当前只有浅色主题。不得仅通过 `prefers-color-scheme` 自动切换为深色，避免网站随 Codex、浏览器或操作系统外观发生未经设计的变化。

未来只有在完成独立深色 token、所有组件验收和明确主题控制后，才增加深色模式。

## 5. 色彩系统

### 5.1 基础 token

| Token | 建议值 | 用途 |
| --- | --- | --- |
| `--color-canvas` | `#F5F1E8` | 全站主背景 |
| `--color-surface-subtle` | `#ECE5D8` | 导读、来源说明、折叠目录等轻区分区域 |
| `--color-text` | `#20211F` | 标题、正文、主要信息 |
| `--color-text-muted` | `#625F58` | 次要说明、元数据、边界说明 |
| `--color-border` | `#C9C3B7` | 仅用于必要控件、焦点辅助和架构关系 |
| `--color-accent` | `#A34322` | 当前导航、链接、编号、内容类型 |
| `--color-accent-strong` | `#7D2F19` | hover、active 和需要更强对比的强调 |
| `--color-focus` | `#7D2F19` | 键盘焦点 |

### 5.2 语义规则

- 正文不得使用强调色。
- 赭色只用于可以解释的状态：链接、当前项、编号、内容类型和交互反馈。
- `surface-subtle` 不是卡片背景，不给所有内容加底色。
- `border` 不用于重新制造 v0.3.1 已经删除的装饰性分隔线。
- 架构图边界可使用 `text-muted` 或专用 `architecture-line`，因为其线条具有业务含义。

### 5.3 对比度合同

- 普通正文和交互文字目标至少达到 WCAG AA `4.5:1`。
- 大标题目标至少达到 `3:1`。
- 当前 `#6D6D66` 在 `#ECE5D8` 上约为 `4.16:1`，不能继续作为浅底区块里的普通小字号文字。
- `text-muted` 调整为 `#625F58` 后，在 `surface-subtle` 上约为 `5.08:1`。
- 焦点不能只依赖颜色，必须保留清楚轮廓。

## 6. 字体系统

### 6.1 字体角色

```text
Display / Editorial
Noto Serif SC → Songti SC → STSong → serif

Interface / Metadata
Noto Sans SC → PingFang SC → Microsoft YaHei → sans-serif

Latin wordmark
Georgia → Noto Serif SC → serif
```

### 6.2 使用规则

衬线用于：

- 首页核心陈述；
- 页面和文章标题；
- 章节标题；
- 长文正文；
- 作品问题陈述；
- 需要形成编辑感的作者定位。

无衬线用于：

- 导航；
- 元数据；
- 内容类型和主题；
- 按钮、目录、状态、来源和边界；
- 高密度观察列表的说明文字；
- 架构图辅助文字。

### 6.3 响应式字体原则

手机端不得把所有衬线角色整体替换成无衬线：

- 标题和长文正文继续使用编辑型衬线；
- 导航、元数据、操作和紧凑列表继续使用无衬线；
- 通过字号、行高和空间适配窄屏，而不是更换品牌语言。

### 6.4 字体加载合同

- 不复制 Maggie Appleton 使用的 Canela 字体文件。
- 第一阶段继续使用具有明确许可的 Noto Serif SC 与 Noto Sans SC。
- Engineering task 必须评估当前 Google Fonts `@import` 的阻塞、稳定性和跨地区访问风险。
- 推荐改为 HTML `<link>` 或经过许可的本地托管资源；如果本地中文字体资产造成不可接受的体积，保留远程字体并确保系统字体回退可用。
- `font-display: swap`。
- 仅加载实际使用的 `400 / 500 / 600` 字重。
- 禁止浏览器合成不存在的粗体和斜体。

### 6.5 中文换行合同

中文标题的“目标行数”和“容器宽度”不能替代语义换行规则。视觉验收必须同时检查完整词组是否被拆开。

适用对象：

- 首页核心陈述；
- 页面标题、文章标题和作品标题；
- 重点观察与重要章节标题。

工程规则：

1. 页面和中文内容必须具有正确的 `lang="zh-CN"` 语言上下文；
2. display、页面标题和文章标题优先使用 `word-break: auto-phrase`，并配合 `text-wrap: balance`；
3. 重点观察和章节标题优先使用 `word-break: auto-phrase`，并配合 `text-wrap: pretty` 或经过验证的 `balance`；
4. 正文保持连续阅读，不为了标题效果改变全局正文断行；
5. 不使用面向单一视口的硬编码 `<br>`，也不通过缩窄容器或散落 media query 人为制造目标行数；
6. 对不支持 `auto-phrase` 的浏览器，先接受正常中文断行回退；只有真实验收证明核心标题持续破坏词义时，才对极少数长期标题使用内容层语义分段，不建立两套响应式文案。

受保护的完整词组包括但不限于：

- `构建`
- `同时`
- `企业数字化`
- `Robotaxi`

验收必须在 1440、1024、768、557、520、390、320px 检查实际断点，而不只检查标题占几行。只要出现“构 / 建”“同 / 时”这类拆词，即使标题宽度和行数达到目标，也不能判定排版通过。

## 7. 字号与行高

字号使用语义 token，通过 `clamp()` 在 390px—1440px 之间平滑变化。

| Token | 桌面目标 | 手机目标 | 行高 | 用途 |
| --- | ---: | ---: | ---: | --- |
| `--type-display` | 60–68px | 36–40px | 1.28–1.38 | 首页核心陈述 |
| `--type-page-title` | 50–56px | 34–38px | 1.32–1.42 | 栏目、文章、作品标题 |
| `--type-section-title` | 28–32px | 24–27px | 1.4–1.5 | 一级内容区 |
| `--type-feature-title` | 27–30px | 22–25px | 1.45–1.55 | 重点观察、作品摘要 |
| `--type-reading` | 17.5–18px | 16.5–17px | 1.9–2.0 | 中文长文 |
| `--type-summary` | 16–18px | 15–16px | 1.75–1.9 | 副标题、摘要、问题陈述 |
| `--type-ui` | 14–15px | 14px | 1.55–1.7 | 导航、目录、行动 |
| `--type-meta` | 12–13px | 12px | 1.5–1.65 | 日期、主题、状态 |
| `--type-caption` | 11–12px | 11px | 1.55–1.7 | 来源、边界、图注 |

约束：

- 不再使用 `9px`、`10px` 作为承载必要信息的常规字号。
- 11px 只用于非核心图注或附加说明。
- 中文 display 字号小于 Maggie 英文 display，因为单个汉字信息密度更高。
- 英文和数字元数据可以适量增加字距；中文正文不增加字距。

## 9. 空间系统

### 9.1 基础尺度

```text
4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96 / 128
```

| Token | 值 | 典型用途 |
| --- | ---: | --- |
| `--space-1` | 4px | 紧密文字关系 |
| `--space-2` | 8px | 元数据内部 |
| `--space-3` | 12px | 标签与标题 |
| `--space-4` | 16px | 小组件内距 |
| `--space-5` | 24px | 内容块内部 |
| `--space-6` | 32px | 组件间距 |
| `--space-7` | 48px | 区块内部 |
| `--space-8` | 64px | 区块间距 |
| `--space-9` | 96px | 页面大区段 |
| `--space-10` | 128px | 桌面首屏与章节节奏 |

### 9.2 流体空间

建议定义：

```text
--gutter-page: clamp(18px, 4vw, 64px)
--space-section: clamp(48px, 7vw, 96px)
--space-hero: clamp(64px, 10vw, 128px)
--space-reading-section: clamp(40px, 6vw, 72px)
```

### 9.3 空间语义

- 元数据与标题：12–20px；
- 标题与摘要：20–28px；
- 摘要与正文：32–48px；
- 正文章节：48–72px；
- 首页大区块：72–112px；
- 手机大区块：48–72px。

不允许每个组件任意创造 18、26、38、52、66 等新尺度。确需例外时必须说明视觉关系。

### 9.4 相邻内容节奏合同

垂直间距由“上一项与下一项是什么关系”决定，不能给所有元素统一设置上下 margin。

| 相邻关系 | 目标范围 | 含义 |
| --- | ---: | --- |
| 同一论述中的正文段落 → 正文段落 | 20–28px | 连续阅读，保持关联 |
| 标题 → 第一段正文 | 16–24px | 标题统领其内容 |
| 正文 → 列表、引用或语义提示 | 20–28px | 同一论述的表达形式切换 |
| 列表项 → 列表项 | 8–14px | 同组对象，不制造章节感 |
| 一个论述结束 → 下一个小标题 | 40–56px | 明确主题转换 |
| 大章节 → 下一大章节 | 56–72px | 表达结构边界 |
| 元数据 → 标题 | 12–20px | 同一内容对象内部 |

工程合同：

1. 优先由父级 flow、相邻选择器或语义组件控制块间距；
2. 同一间距关系只能由一个责任方定义，避免上一项 `margin-bottom` 与下一项 `margin-top` 叠加；
3. 不依赖未经设计的 margin collapse 得到页面节奏；
4. 内容数据不写视觉空行、空段落或 `<br>` 来制造距离；
5. 桌面与手机可以缩放节奏，但必须保留“对象内部更紧、对象之间更疏”的关系；
6. 验收必须查看上一项和下一项的组合，不能只测单个元素的计算样式。

### 9.5 视觉结构对象模型

空间不是元素自己的装饰属性，而是对象关系的投影。全站视觉结构固定为六层：

```text
L0 Page Frame      页面版心、首尾边界和全局阅读方向
L1 Section         观察、作品、About 等独立栏目
L2 Content Group   栏目导语、重点内容、归档、证据组
L3 Content Object  一篇观察、一项作品、一个能力或一个项目
L4 Element         序号、类型、标题、说明、状态、行动
L5 Relationship    上一对象与下一对象之间的邻接关系
```

判断规则：

- L4 元素不能自行决定它和外部对象的距离；
- L3 对象负责自己的内部构成，但不负责与下一个同级对象的距离；
- L2 父级 flow 统一定义同级 L3 对象之间的节奏；
- L1 栏目只表达栏目内部结构；栏目之间的距离由 L0 页面流负责；
- 换模板时可以改变网格、方向、字号和外观，但必须保留内容对象、对象层级与邻接关系。

### 9.6 空间关系 token

不要把 `16 / 24 / 48 / 96` 直接理解成固定元素 margin。先判断关系，再映射到 token：

| 关系 token | 桌面参考 | 手机参考 | 典型关系 |
| --- | ---: | ---: | --- |
| `--rhythm-bind` | 8–12px | 8–10px | 类型 → 标题、标题 → 紧密说明 |
| `--rhythm-relate` | 16–24px | 14–20px | 标题 → 摘要、正文 → 行动 |
| `--rhythm-object` | 32–48px | 28–40px | 栏目导语 → 第一项内容、对象内部主要分组 |
| `--rhythm-group` | 48–64px | 40–56px | 同栏目的内容对象 → 下一对象 |
| `--rhythm-section` | 96–128px | 64–88px | 一个栏目 → 下一栏目 |

数值是当前视觉主题的实现参数，关系 token 和层级才是可迁移合同。未来更换模板时可以重新标定数值，但不能把 `section` 关系降成 `bind`，也不能把对象内部关系放大成栏目边界。

### 9.7 间距责任

每一段垂直距离只能有一个责任方：

```text
页面边缘       → Page Frame
栏目之间       → Page Stack
栏目导语与内容 → Section Flow
同类对象之间   → Collection Flow
对象内部语义组 → Object Stack
组内元素       → Element Relationship
```

禁止：

- 上一栏目保留 `padding-bottom`，下一栏目再保留等量 `padding-top`；
- 每个组件同时设置外部 `margin-top` 与 `margin-bottom`；
- 用空节点、空段落或内容字段制造留白；
- 因对象内容变长而改变同级对象之间的基础关系；
- 在页面 CSS 重新定义组件已经拥有的内部节奏。

推荐：

- 页面级 `stack` 统一拥有栏目间 `gap`；
- collection 统一拥有同类对象间 `gap`；
- 内容对象内部拆成 `identity / proposition / evidence / action` 等语义组；
- 原始元素先进入语义组；组内使用 `bind`，相邻语义组通常使用 `relate`，只有对象内部确实存在独立主要分区时才使用 `object`；
- `ObjectStack` 的默认节奏是 `relate`，不能因为它承载 Content Object 就机械映射为 `--rhythm-object`；
- 对象间使用 `group`，栏目间使用 `section`；
- 通过结构测试检查责任，通过 Chrome 截图检查实际节奏。

### 9.8 结构层级与构图层级不可混用

六层模型回答“对象属于哪里”，空间 token 回答“两个相邻对象是什么关系”。对象层级较高，不代表它内部所有元素都应使用更大的间距。

错误推导：

```text
这是 Content Object
→ 使用 ObjectStack
→ 所有直接子元素统一使用 --rhythm-object
```

正确推导：

```text
Content Object
├─ Identity
├─ Proposition
├─ Evidence
└─ Action

Identity → Proposition：relate
Proposition → Evidence：relate，或经验证后使用 object
Evidence → Action：relate
对象 → 下一对象：group
```

验收时必须同时检查：

- 结构是否有正确语义角色；
- 角色之间使用的关系是否正确；
- 实际视觉距离是否让对象仍被感知为一个整体。

如果一个内容对象内部的每个元素看起来像四个独立区块，即使类名完整、token 合法，也不能判定结构系统实现正确。

### 9.9 数字、序号与标签语义合同

数字不是建立结构感的通用装饰。任何可见数字必须回答一个明确问题：

| 数字类型 | 回答的问题 | 是否保留 |
| --- | --- | --- |
| 顺序 | 这是第几步，前后顺序是否影响理解？ | 保留 |
| 排名 | 它在明确排序中位于第几？ | 保留 |
| 稳定索引 | 其他内容是否通过该编号引用它？ | 有引用价值时保留 |
| 位置 | 当前是已知序列中的第几项？ | 交互确有需要时保留 |
| 数量 | 集合一共有多少项？ | 数量帮助判断范围时保留一次 |
| 时间 | 内容何时发布、更新或属于哪一年？ | 使用日期或年份，不包装成序号 |
| 装饰编号 | 只为页面显得“结构化” | 删除 |

xingbuild 当前合同：

- 首页“最新观察、核心作品、关于我”已经有唯一栏目标题，不再显示 `01 / 02 / 03`；
- 观察按时间排序，使用发布日期和年份分组，不增加内容序号；
- 作品是并列成果，使用名称、类型、状态和更新时间，不增加 `01 / 02`；
- 核心能力和“能够解决的问题”是并列集合，不使用顺序编号；
- 作品详情中的主题说明是并列内容，不使用序号；
- 架构流程和四个平面保留 `01–05 / 01–04`，因为数字表达顺序或稳定架构位置；
- `404`、版本号和确有意义的集合数量属于标识或状态，不视为装饰编号。

同一页面不得让栏目编号、内容编号、流程编号共享同一种外观却承担不同含义。数字的颜色、字号和位置必须服从其语义角色。

## 10. 页面网格

### 10.1 版心

```text
--page-max: 1280px
--content-max: 1040px
--reading-max: 720px
--page-gutter: clamp(18px, 4vw, 64px)
```

### 10.2 桌面

- 以 12 列编辑网格为概念模型；
- 首页标题占约 8–10 列；
- 正文目录占 2 列，正文占 7 列，余下空间作为呼吸区；
- 观察元数据与标题列对齐，但不强行填满所有列；
- 作品可以使用文字与架构图的非对称双列。

### 10.3 手机

- 单列是默认，不模拟桌面表格；
- 保持 18–22px 页面边距；
- 元数据允许换行；
- 目录、筛选和菜单成为独立状态；
- 架构图按业务顺序改为纵向；
- 任何组件都不得造成整页横向滚动。

## 11. 响应式规则

使用内容驱动断点：

| 区间 | 责任 |
| --- | --- |
| `>= 1200px` | 宽桌面，完整编辑网格 |
| `900–1199px` | 标准桌面/窄桌面，减少空白列 |
| `640–899px` | 紧凑布局，复杂双列开始重组 |
| `< 640px` | 手机单列，菜单和目录进入独立状态 |

核心规则：

1. 颜色角色不随断点变化。
2. 字体角色不随断点整体变化。
3. 标题和空间通过 `clamp()` 平滑缩放。
4. 只有结构无法保持可读时才切换布局。
5. 桌面目录到紧凑布局后折叠。
6. 桌面元数据列在手机改为标题上方的横向换行组。
7. 作品图在手机变成纵向流程，不缩小桌面图。

## 12. 组件视觉合同

### 12.1 SiteHeader

- 桌面高度 80–88px，品牌在左，三项导航在右。
- 手机高度 64–72px，品牌与 44px 菜单按钮并列。
- 当前导航使用强调色；不使用胶囊或底色。
- 展开菜单是完整状态，必须锁定正文并支持关闭、Escape 和导航恢复。
- 手机菜单只显示一级栏目名称，不增加序号、英文副标题、说明、日期或数量。
- 手机菜单文字使用编辑型衬线约 23–25px、行高 1.4–1.5；三项导航保持 52–56px 触控高度、8–12px 项间距。
- 第一项从页头下方约 24–32px 开始；当前页只通过强调色和 `aria-current` 表达。

### 12.2 HeroStatement

- 只包含作者标识、核心陈述和一段范围说明。
- 标题使用 `display`，正文使用 `summary`。
- 不放状态卡、所在地或多项操作。
- 桌面首屏能够看见下一区块的开始。

### 12.3 SectionIntro

- 可选语义标签、标题、说明和可选行动组成稳定结构。
- 标签只用于类别、状态或确有意义的索引；不能为了构图自动生成编号。
- 标签和行动使用无衬线；标题使用衬线。
- 手机上行动与标题不能争夺同一行空间，必要时下移。

### 12.4 ObservationFeature

- 元数据、标题、摘要、继续阅读。
- 不增加包围卡片。
- 摘要最大两至三行；完整内容进入正文。

### 12.5 ObservationRow

- 桌面：元数据列 + 标题/可选摘要 + 方向提示。
- 手机：元数据在上、标题在下，摘要仅重点内容显示。
- 整行可点击，焦点可见；方向箭头不能成为唯一链接提示。

### 12.6 ArticleHeader

- 返回路径、元数据、标题、摘要、可选问题导读。
- 标题与摘要使用不同色阶和字号，不靠背景分割。
- 导读区只在分析文章确有必要时显示。

### 12.7 ArticleToc

- 桌面 sticky，字号至少 12px。
- 手机使用原生 `details/summary` 或等价可访问控件。
- 当前章节状态以后可增加，但不是 v0.4.0 必需项。

### 12.8 Prose

- 正文使用编辑型衬线。
- 段落字号和行高遵守阅读 token。
- H2 与正文之间以空间建立层级。
- 引用、列表、表格、代码、图注分别定义，不继承浏览器偶然默认值。
- 外部链接、内部链接和引用来源保持可辨识。

### 12.9 WorkSummary

- 问题 → 构建对象 → 状态 → 证据边界 → 可选架构摘要。
- 首页不默认显示完整架构图。
- 状态与边界使用 UI 字体，不与作品标题竞争。

### 12.10 ArchitectureDiagram

- 节点、顺序、边界和反馈具有业务含义。
- 桌面可横向，手机必须重新排列为纵向。
- 文字最小 12px，重要节点不小于 14px。
- 线条不是装饰，不能与普通分隔线混用。

### 12.11 EvidenceNote

- 用于来源、状态、假设和证据边界。
- 使用 `surface-subtle`，但文字必须达到正常字号对比度。
- 不得将计划、参与或推断包装成已验证结果。

### 12.12 FrameworkExplorer

- 认知框架使用同一知识模型投影总览、局部结构、概念详情、底层追溯和应用，不为不同页面复制定义。
- 宽桌面采用主图与右侧稳定详情并列；详情不遮挡主图、不建立内部滚动容器。
- 900px 以下改为单列，手机概念详情进入独立页面；完整定义不放入底部抽屉。
- 手机总览按关系语义重排为纵向流，不缩小桌面关系图，不依赖横向拖动。
- 关系线只表达有名称的真实关系，并提供文字等价物。
- 当前节点、路径和关系同时使用文字、形态或线宽表达，不能只依赖颜色。
- 路径、定义依赖、相关概念和应用入口是不同关系角色，不得合并成一组无差别链接。
- 概念页保留来源视图、认知路径、上游版本和返回现场所需状态。

## 13. 交互状态

所有链接、按钮、菜单和目录至少定义：

- default；
- hover；
- focus-visible；
- active/current；
- disabled（存在时）。

规则：

- hover 不得导致文字或布局跳动；
- 焦点轮廓至少 2px，外偏移 3–5px；
- 触控目标至少 44×44px；
- 动画控制在 120–220ms；
- `prefers-reduced-motion: reduce` 时移除非必要平滑滚动和过渡；
- 菜单、目录展开必须向辅助技术表达状态。

## 14. 图形和资产

- 站点不使用图形 Logo，`xingbuild` 继续是文字标识。
- 图标来自已选图标库，不使用 Unicode 符号模拟核心控件。
- 不使用手绘、植物、景观、渐变光效或装饰性 3D。
- 作品和文章插图必须解释业务对象、关系、顺序、指标或证据。
- 图片必须提供尺寸、替代文本和加载策略。

## 15. 工程结构合同

### 15.1 CSS

建议从单一 `src/styles.css` 演进为：

```text
src/styles/
├─ tokens.css
├─ foundations.css
├─ layout.css
├─ components.css
└─ pages.css
```

根 `src/styles.css` 只负责按顺序导入。推荐使用 CSS cascade layers：

```text
tokens → reset/foundations → layout → components → pages
```

响应式规则与所属组件放在同一责任文件，避免建立一份无法追踪责任的全局“mobile.css”。

### 15.2 React

当前 `App.jsx` 同时承担路由、页面和组件。v0.4.0 只拆分已经稳定并重复使用的责任：

```text
src/components/site/
src/components/content/
src/components/reading/
src/components/works/
src/pages/
```

不为每个标签创建组件，不引入新的 UI 框架或运行时。

### 15.3 内容、表现和 token

```text
siteContent.js     内容事实与关联
components/        语义表现和交互
styles/tokens.css  视觉决策
pages/             页面编排
```

页面不得复制内容事实；组件不得自行判断作品状态；token 不包含业务含义。

## 16. 验证合同

### 16.1 视口

至少验证：

- 1440×1000；
- 1024×768；
- 768×1024；
- 390×844；
- 320×568。

### 16.2 页面

- 首页；
- 观察列表；
- 短观察；
- 分析长文；
- 作品列表；
- 作品详情；
- 关于我；
- 手机菜单打开状态；
- 手机目录打开状态。

### 16.3 可见检查

- 字体是否实际加载、回退是否可接受；
- 标题换行是否自然；
- 正文行宽和行高是否稳定；
- 必要小字是否达到设计最小值；
- 色彩对比是否满足合同；
- 焦点是否可见；
- 320px 是否无整页横向滚动；
- 桌面与手机是否保持同一品牌；
- 无装饰性边框和卡片回潮；
- 架构图在手机是否仍可读。

### 16.4 自动检查

应增加或更新：

- token 存在性和禁止值检查；
- 响应式规则不重定义全局品牌颜色；
- 必要内容组件使用语义 class；
- 不出现小于 11px 的必要文本；
- `prefers-reduced-motion` 存在；
- 核心内容对象与路由继续通过原测试；
- `npm run release:check` 全部通过。

## 17. 演进边界

Visual System v1 当前不包含：

- 深色主题；
- CMS 编辑器视觉规范；
- 数据仪表盘图表系统；
- 微信公众号和 X 渠道模板；
- 复杂动画系统；
- 插画系统；
- 完整组件展示站或 Storybook。

当组件数量、协作人数或回归成本明显增加时，再评估 Storybook、视觉回归服务或更完整的 design token 构建工具。
