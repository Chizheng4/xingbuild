# v0.21.0 Practice 内容独立发布能力方案

> 状态：已确认的 `v0.21.0` 实施方案
> 责任：产品与视觉 task 维护产品与发布合同；内容与发布 task 负责内容准备、人工复核和发布；Engineering 只实现发布能力
> 目标版本：`v0.21.0`
> 上位事实源：[`docs/product/xingbuild 网站产品架构与视觉系统总案.md`](../product/xingbuild%20网站产品架构与视觉系统总案.md)
> 版本排队：[`docs/iterations/roadmap.md`](../iterations/roadmap.md)

本文只解决“已批准的 B 端 Practice 内容可以像 Article 一样按单一目标独立检查、提交和发布”。它不改变 `/products` 的页面结构、视觉、Practice 内容 schema 或读者互动，也不实现通用能力展示控件。

## 1. 本版本解决的问题

当前 `Practice` 已有内容对象、媒体 manifest、来源边界和 `practice:check`，但缺少目标级 scope check 与独立发布入口：

- 内容 task 修改 Robotaxi Practice 后无法使用与 Article/Observation 等价的单目标发布命令；
- 生产发布容易与产品版本、UI 工程或其他内容混在一起；
- 现有媒体生命周期已经要求 approved/public/hash，但发布前没有统一的目标文件、版本和公网验收门禁。

本版本的成功定义：

```text
更新一个已批准 Practice
  = Practice 内容 + 对应 approved/public media manifest/asset
  + Practice checks + scope check
  + 独立内容提交 + publish-practice --id <id>
  ≠ 页面 JSX/CSS + 产品版本/tag + 全站工程迭代
```

## 2. 目标与明确不做

### 2.1 目标

1. 以稳定 `practice id` 为目标，支持单一 Practice 内容包检查和发布；
2. 强制校验 Practice schema、模块媒体关系、manifest 审批状态、文件存在性与 SHA-256；
3. 强制目标提交范围，只允许目标 Practice JSON、对应 manifest 和必要的已批准媒体文件；
4. 保持产品版本和 tag 不变，独立 push、EdgeOne 部署和目标公网验收；
5. 让内容 task 可以在既有 `/products` 组合中更新标题、说明、模块和已批准媒体，不修改页面组件。

### 2.2 明确不做

- 不实现 `CapabilityHost / VisualizationHost`、LikeC4 多视图、Mermaid 新 adapter 或自由画布；
- 不嵌入 Robotaxi 独立系统，不改变登录、权限、访问记录、`action.href` 语义或安全边界；
- 不增加 `HybridComposition`、长文嵌入、B 端页面新区域、新的视觉 token 或响应式布局；
- 不扩展 Practice schema，不增加页面专用字段、坐标、路径、视口 CSS 或任意 JSX；
- 不支持多 Practice 批量发布，不支持把 Observation、Article、About、规则、worker 或工程文件混入；
- 不由命令选题、写稿、事实审核、批准 Robotaxi 状态或自动修改内容。

## 3. 当前事实与对象边界

### 3.1 事实源

- Practice 内容：`content/products/<practiceId>.json`；
- Practice 媒体 manifest：`content/media/<practiceId>/manifest.json`；当前真实目标为 `robotaxi`；
- 公开媒体：manifest `src` 对应的 `public/media/<practiceId>/...`；
- 非公开归档媒体：manifest `archivePath` 对应的 `content/media/<practiceId>/archive/...`；
- 上游 Robotaxi 系统状态、版本、commit 和审批事实仍由 Robotaxi 项目提供；xingbuild 只保存批准后的展示快照。

### 3.2 读者可见与内部字段

读者只看到 Practice 的标题、介绍、边界、模块说明、已批准媒体和可选独立系统链接。`reviewStatus`、`publicStatus`、`approvalRecord`、`provenance`、hash、治理理由和暂停状态只用于生产检查，不投影到页面。

只有以下条件同时成立，模块媒体才允许进入生产读取层：

```text
manifest.reviewStatus = approved
manifest.publicStatus = public
manifest.currentPublication.status = active
asset.reviewStatus = approved
asset.provenance.approvalStatus = approved
asset.publicStatus = public
asset.src 非空且位于对应 media 目录
本地文件 SHA-256 == manifest.assetSha256
```

任何 pending、paused、revoked、internal、superseded 或 hash 不一致的记录必须失败或继续留在内部归档，不得静默降级为公开媒体。

## 4. 内容 task 的日常路径

1. **上游交接**：Robotaxi 产品管理 task 提供已确认系统状态、版本锚点、素材清单、来源和状态边界；不直接写网站页面代码。
2. **内容准备**：内容与发布 task 只修改目标 Practice 内容和已批准媒体 manifest/asset，复核标题、模块顺序、说明文字、边界和阅读友好性。
3. **本地预览**：使用既有本地服务查看 `/products`，确认页面结构、媒体比例、空态和 `action` 入口；不因内容增加写 CSS 或 JSX。
4. **目标检查**：运行 `npm run practice:check` 与 `npm run practice:scope-check -- --id <practiceId> --commit HEAD`。
5. **独立提交**：只提交目标 Practice 包；产品版本、`VERSION.md`、tag、页面代码、规则和其他内容不得进入提交。
6. **发布**：运行 `./publish-practice.command --id <practiceId>`，脚本执行检查、构建、Sites test、push、EdgeOne 和目标公网验收；命令不创建 commit、不创建产品 tag。
7. **失败重试**：push、部署或公网验收失败时保留同一 commit，修复外部状态后在同一 HEAD 重试，不创建替代提交；无关 workspace 不得被扫描、删除或阻断。

## 5. 命令合同

### 5.1 `practice:scope-check`

命令：

```bash
npm run practice:scope-check -- --id <practiceId> [--commit HEAD]
```

硬门槛：

- `--id` 必须唯一、非空、kebab-case；当前允许的真实 id 为 `robotaxi`；
- commit 必须包含 `content/products/<id>.json`；
- 允许文件只能是目标 Practice JSON、对应 `content/media/<id>/manifest.json`、manifest 当前引用的必要 public/archive 媒体文件；
- 修改了其他 Practice、Observation、Article、About、页面、样式、脚本、配置、规则、版本或 worker 时失败；
- commit 不得改变 `package.json`/`VERSION.md` 版本，不得创建 tag；
- `origin/main` 必须等于 `HEAD^`（首次推送）或等于 `HEAD`（同一 HEAD 重试）；
- 必须调用现有 `validatePracticeBundle` 和文件/hash 校验，不得复制另一份 Practice schema。

### 5.2 `publish-practice.command`

命令：

```bash
./publish-practice.command --id <practiceId>
```

脚本责任：

1. 确认当前分支为 `main`、工作区干净、origin 为预期 xingbuild 仓库；
2. 执行 `practice:check`、目标 `practice:scope-check`、`npm run build`、`npm run test:sites`；
3. 确认产品版本与父提交一致、没有产品 tag、目标提交 scope 通过；
4. 在 `origin/main == HEAD^` 时 push `main`；若已经是同一 HEAD，允许部署/公网验收重试；
5. 将同一 commit 的 `dist/client` 部署到既有 EdgeOne `xingbuild-nochina` 项目；
6. 调用目标 `verify-practice-release`，核对 release/content manifest 版本与完整 SHA、目标 Practice id、模块和公开媒体；
7. 任一步失败都停止并返回可诊断错误，不自动修改、回滚或删除内容文件。

命令明确不负责：commit、tag、选题、写稿、人工审核、审批媒体、修改无关文件、清理 workspace、更新产品版本或发布 Robotaxi 独立网站。

## 6. Engineering 实现边界

允许修改：

- `package.json`/锁文件中本版本所需的命令入口，不升级无关依赖；
- `scripts/practice-scope-check.mjs`；
- `publish-practice.command`；
- `scripts/verify-practice-release.mjs`；
- `scripts/lib/practice-content.mjs` 的复用型校验扩展；
- 对应 `tests/` 专项、规则中的 Practice 发布段落和本版本 QA/文档。

禁止修改：

- `src/` 页面、组件、CSS、视觉 token、路由和 PageDefinition 组合；
- Practice schema、Robotaxi 业务事实、manifest 审批结论或媒体内容（除非 Engineering 仅为测试 fixture，且不得进入生产）；
- Observation、Article、About、产品版本/tag、EdgeOne 项目配置、Robotaxi 仓库或独立系统登录能力；
- 任意未确认 DRAFT、无关 docs 修改、候选/审核 workspace。

若发现 schema、媒体来源或上游状态不足，Engineering 必须报告缺口并停止，不得用页面占位或猜测内容通过发布。

## 7. 验收合同

### 7.1 自动与范围验收

- 正常 Practice 包通过 `practice:check`、scope check、build、Sites test；
- 缺少模块媒体、重复 id、非法 action、manifest 未 approved/public、hash 不符、文件缺失、跨 Practice 文件、代码/UI/版本混入均硬失败；
- 单一目标提交的允许路径集合可复现，禁止通配清理；
- 同一 HEAD 的部署/公网失败重试不会创建替代 commit；
- 内容发布不改变产品版本/tag，生产 bundle 不读取 `.content-workspace`。

### 7.2 读者与响应式验收

- `/products`、首页 Practice 投影和 Observation rail 继续使用同一 Practice 内容对象；
- 1440px、768px、390px 至少各验证一次：标题/模块归属、媒体比例、空模块不占位、无横向溢出、console error/warning=0；
- 内容增加或减少模块只改变自然流内容，不改变页面组件、版心、字体角色和关系间距；
- 读者界面不展示治理状态、hash、来源审批字段或内部路径；
- `action` 仍是经批准的独立 Robotaxi 入口，不在 xingbuild 内默认登录或嵌入系统。

### 7.3 发布验收

- GitHub main、EdgeOne、`release.json`、`content-manifest.json` 和目标 Practice 公网内容为同一完整 commit SHA；
- 产品版本保持 `v0.20.0`；
- 目标公网 URL 验收通过后，分别回传实现、验证、commit、push、部署和公网结果；
- 版本完成后归档本方案，清空 `current.md`，并把 `CapabilityHost / VisualizationHost` 保留为后续候选，不自动开启下一版本。

## 8. 后续演进边界

当真实 Practice 内容反复证明需要统一图片、视频、架构图或受控互动空间时，另立 `CapabilityHost / VisualizationHost` 版本方案。该版本不因发布 CLI 的完成而自动进入实现，也不允许把 LikeC4、Mermaid、Robotaxi embed 和页面重构捆绑进来。
