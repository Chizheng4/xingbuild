# v0.20.0 页面定义注册与组合渲染方案

> 状态：已确认的 `v0.20.0` 实施方案（原 DRAFT 已正式转正）
> 责任：xingbuild 产品与视觉 task 维护产品合同；Engineering 负责实现与验证  
> 目标版本：`v0.20.0`
> 上位事实源：[`docs/product/xingbuild 网站产品架构与视觉系统总案.md`](../product/xingbuild%20网站产品架构与视觉系统总案.md)  
> 版本排队：[`docs/iterations/roadmap.md`](../iterations/roadmap.md)

本文只解决“页面组合从文档合同变成最小可执行注册能力”，不重做网站、不实现图形运行时，也不改变当前公开内容。已进入 `docs/iterations/current.md` 后，Engineering 只能按本文范围实现；本文不授权 push、部署或发布。

## 1. 为什么需要这个版本

当前网站已经有稳定的页面母版和内容对象，但页面组合主要仍通过路由和页面组件接线。结果是：

- 增加一个同类页面可能需要新增页面 JSX 或路由分支；
- 页面左右区域、目录、长文和能力空间的组合规则容易被页面代码重复实现；
- 内容运营已经可以更新文章和图形，但还不能可靠地声明“使用哪个页面组合”；
- 产品方案中的 `PageDefinition → PageComposition` 尚未成为可执行、可校验的运行时合同。

本版本只把这一层补齐，证明“新增同组合页面可以配置化接入”这个长期目标，而不是一次性完成所有页面平台能力。

## 2. 目标与成功定义

### 2.1 目标

1. 建立受控的 `PageDefinition` registry（页面注册表）；
2. 用共享 composition renderer（组合渲染器）承接既有页面结构；
3. 用一页低风险真实页面完成迁移验证，推荐 `/about`；
4. 用一个同组合 fixture（验证样例）证明新增页面不需要新页面 JSX、页面 CSS 或重复路由分支；
5. 保持已有 URL、内容 schema、视觉 token、返回导航、内容发布和产品版本边界不变。

### 2.2 成功定义

```text
新增同组合页面
  = 页面定义 + 已批准内容对象
  ≠ 新页面组件 + 页面专用 CSS + 路由分支
```

成功不等于任何人都可以写任意页面配置；成功意味着有限、可校验、可验收的页面组合可以被复用。

## 3. 事实源与范围边界

### 3.1 必须继承的事实

- 一级导航仍为 `B端产品 / 经营观察 / 关于我`；
- 页面组合和共享区域以产品/视觉总案为唯一基线；
- 当前公开版本为 `v0.19.0`；
- `ObservationPublication`、`EvergreenArticlePublication`、`Practice`、`Profile` 的事实边界不变；
- Header、Footer、ReadingShell、ShowcaseLayout、ReturnNavigation 和现有视觉 token 不改写；
- 内容发布仍保持产品版本/tag 不变。

### 3.2 本版本只允许修改

- 页面定义的受控 schema 和校验；
- 页面组合的共享渲染接线；
- 必要的路由解析适配；
- 一个低风险真实页面迁移；
- 一个同组合新增页面的测试/验证样例；
- 对应自动测试、文档和验收证据。

### 3.3 明确不做

- 不实现 `VisualizationHost / CapabilityHost`；
- 不实现 LikeC4 原生 runtime、多视图浏览器、自由画布或任意图形布局；
- 不嵌入 Robotaxi 独立系统，不改变登录、权限、访问记录或素材边界；
- 不迁移全部历史页面，不删除旧实现，不修改 Observation 短文 schema；
- 不改变品牌色、主题、Header、Footer、一级导航或发布命令；不提前开启 `v0.21.0`。`v0.20.0` 的标准版本记录、commit/tag 和收口检查属于本版本交付，不是额外范围；
- 不允许内容 task 提交 JSX、CSS、节点坐标、关系路径或任意 renderer 配置。

## 4. 产品模型

### 4.1 页面定义

页面定义是页面责任和内容引用的受控声明，不是业务事实源：

```text
PageDefinition
├─ id
├─ route
├─ navigationEntry?
├─ intent
├─ composition
├─ regions
├─ contentRefs
├─ capabilities?
├─ navigationContext
├─ responsivePolicy
└─ acceptance
```

字段规则：

| 字段 | 产品责任 | 约束 |
| --- | --- | --- |
| `id` | 稳定页面身份 | 唯一、不可按视口变化 |
| `route` | 安全站内目标 | 不得与既有路由冲突；参数必须经过校验 |
| `composition` | 选择共享页面组合 | 只能使用已注册组合枚举 |
| `regions` | 选择可选区域 | 只能声明 `TopBand`、`left`、`right`、`body`、`rail`、`RichDocument`、`ClosingSection` |
| `contentRefs` | 引用已批准内容对象 | 不复制内容正文或上游事实 |
| `navigationContext` | 返回目标、焦点和安全 `origin/returnTo` | 不只依赖 `history.back` |
| `responsivePolicy` | 选择共享响应式策略 | 不允许写页面专用断点、宽高或坐标 |
| `acceptance` | 声明页面应通过的合同 | 不能降低全站 QA 门槛 |

### 4.2 允许的组合

首版只实现既有且稳定的四种组合：

| 组合 | 现有用途 | 首版要求 |
| --- | --- | --- |
| `HomeComposition` | 首页对象投影 | 保持现有唯一 H1 和对象复用 |
| `ShowcaseComposition` | B端产品展示 | 保持说明区、SystemStage、rail 边界 |
| `CollectionComposition` | 观察集合 | 保持 Brief 结构和无空 rail 规则 |
| `ReadingComposition` | Article、About、长文 | 保持 TOC、RichDocument、返回和锚点 |

`HybridComposition` 与 `CapabilityComposition` 已在产品总案中保留，但不作为本版本的首个运行时范围；它们进入后续版本时必须重新形成明确 DRAFT。

### 4.3 菜单与页面定义

```text
菜单：只提供导航目标
PageDefinition：选择页面组合
内容对象：提供公开内容
共享 renderer：投影结构和视觉
```

新增内容不能通过修改菜单来改变页面结构；新增一级导航也不能仅通过内容文件暗中出现，必须经过产品/视觉确认和版本合同。

## 5. 运行与内容边界

### 5.1 内容 task 可以做什么

- 在已经批准的页面组合中新增或更新 Article、Brief、Practice 或 About 内容；
- 引用已经批准的 `contentRefs`；
- 运行对应 content/article checks 并独立发布；
- 反馈内容确实需要新区域或新能力的证据。

### 5.2 内容 task 不可以做什么

- 新增 `PageDefinition` 中未批准的组合、区域或 renderer；
- 修改页面组件、视觉 token、路由规则或产品总案；
- 在内容文件中写坐标、路径、视口专用 CSS 或任意 JSX；
- 以新增内容为理由开启 `v0.20.0` 或后续产品版本。

### 5.3 失败与降级

- 页面定义 schema 无效、路由冲突、内容引用不存在时构建硬失败；
- 不允许静默回退到另一个页面组合；
- 运行时异常只使用已批准的通用错误或文本降级，不改变页面几何；
- 无有效可选区域时不渲染空 rail、空列或占位框。

## 6. 迁移策略

1. 先冻结当前 v0.19.0 公开行为和 URL 清单；
2. 注册现有页面的最小定义，不改变读者可见结构；
3. 迁移 `/about` 作为低风险真实页面；
4. 用同一 `ReadingComposition` 增加一个本地验证样例，证明配置化接入；
5. 通过桌面、紧凑宽度、手机、键盘、直接访问和返回验收；
6. 只有迁移和样例都稳定后，才评估是否迁移其他组合；
7. 版本完成后记录实际偏差，不把未来 `CapabilityHost` 自动带入下一版。

## 7. Engineering handoff 要求

进入 `current.md` 后，交给 Engineering 的 handoff 必须引用本文并明确：

- 唯一版本和目标 commit 范围；
- 允许修改的 schema、renderer、路由适配和测试文件；
- 明确禁止修改的内容、视觉 token、Observation、Robotaxi、发布命令和无关页面；
- `/about` 迁移和新增 fixture 的验收路径；
- 失败硬门槛、回退方式、资源释放和回传 task；
- 实现、验证、commit/tag、push、deploy、公网验收分别回传。

Engineering 不负责决定页面组合、公开内容或上游事实；发现相邻需求时登记为后续问题，不顺手实现。

## 8. 验收合同

### 8.1 结构

- 页面注册表中每个 `id` 唯一，组合和区域只来自受控枚举；
- 既有 `/`、`/products`、`/business-observations`、`/about`、`/observations` 和文章路径保持可访问；
- 新增样例只增加页面定义和内容引用，不增加页面 JSX、CSS 或专用路由分支；
- 上层页面、菜单、返回目标和内容对象没有第二份事实源。

### 8.2 视觉与响应式

- 桌面、紧凑宽度和手机保持既有视觉 token、顺序和对象归属；
- 可选区域关闭后无空白占位、无异常内部滚动和无横向溢出；
- hover、focus、click、tap 和键盘操作不改变页面整体几何；
- Header、Footer、ReturnNavigation、TOC 和 Article/Brief 投影无回归。

### 8.3 工程与发布

- schema、路由、内容引用和构建失败均可明确诊断；
- `npm run release:check` 及项目既有专项测试通过；
- closeout、preflight、commit/tag、push、部署、公网验收分别记录；
- 内容发布仍可在产品版本不变的情况下单 slug 独立完成；
- 浏览器、本地服务和临时资源在验收结束后释放。

3. 是否同意把 `HybridComposition`、`CapabilityHost`、LikeC4 runtime 和 Robotaxi embed 排到后续版本；
4. 是否同意通过验收后再把其他页面逐步迁移，而不是一次性重写全站。
