# 阅读路径与响应式布局升级方案 v0.3.0

## 1. 方案状态

- 状态：已实施并完成本地验证
- 设计日期：2026-07-25
- 设计责任：网站产品与视觉分析 task
- 实施责任：Engineering 网站迭代 task
- 参考机制：Maggie Appleton 的站点定位、内容集合、列表扫描与长文响应式重组
- 适用范围：首页、观察列表、观察正文，以及作品和关于我的必要上下游适配

本方案不复制 Maggie Appleton 的花园、生长阶段、手绘插画或内容类型数量，只吸收其让访问者快速理解、判断和进入阅读的结构机制。

## 2. 本轮要解决的问题

当前网站已经建立 `xingbuild / 金星 · Xingjin / 观察 / 作品 / 关于我` 的基本结构，但阅读路径仍存在四个问题：

1. 首页首屏同时承担定位、当前关注、最新更新、所在地等任务，主次不够清楚。
2. 三个栏目虽然命名明确，但栏目用途仍需要读者自行推断。
3. 观察列表中的每条内容表达密度相近，不利于区分最新、重点和普通归档。
4. 长文具备正文结构，但进入正文前缺少稳定的“内容是什么、讨论什么、是否适合继续读”的阅读契约。

根本问题不是缺少视觉装饰，而是页面层级没有稳定地回答：

```text
这是谁的网站
    ↓
这里持续发布什么
    ↓
当前这项内容是什么
    ↓
是否值得继续阅读
    ↓
如何继续深入
```

## 3. 设计原则

### 3.1 一层只回答一个主要问题

- 页头负责品牌、作者和全站方向。
- 首页首屏负责网站定位。
- 首页内容区负责提供最新观察和核心作品入口。
- 列表负责扫描和选择。
- 正文页负责理解和深入。

不要在首页首屏同时完成作者简历、作品状态、所在地和全部研究方向介绍。

### 3.2 先解释，再展示

首页和栏目页的区块标题之后增加一句短说明。说明用于定义内容对象，不写宣传口号。

### 3.3 统一对象，不同投影

观察内容由同一结构化对象生成首页摘要、归档行和正文页，不为三个页面维护三套内容。

### 3.4 轻松来自节奏，不来自均匀留白

- 定位区疏；
- 最新内容适中；
- 归档列表紧凑；
- 正文重新收窄。

全站不使用尺寸相同的大卡片堆叠。

### 3.5 响应式是信息重组，不是等比例缩放

桌面与手机使用同一内容和组件语义。断点只调整顺序、密度、显隐、导航、正文宽度和架构图方向。

## 4. 全站身份与页头

### 4.1 桌面页头

```text
xingbuild
金星 · Xingjin                         观察   作品   关于我
```

- `xingbuild` 是第一识别层。
- `金星 · Xingjin` 是作者署名，字号和对比度低于站点名称。
- 三个栏目保持唯一一级导航。
- 当前栏目使用赭色文字或短下划线标识，不增加胶囊背景。

### 4.2 手机页头

```text
xingbuild                                      菜单
```

- 作者身份进入菜单顶部或首页定位区，不挤入窄屏页头。
- 菜单展开后直接显示 `观察 / 作品 / 关于我`，不得增加新的一级入口。

## 5. 首页布局

### 5.1 桌面信息顺序

```text
页头

网站定位
├─ 一句核心陈述
└─ 一句研究与构建范围说明

最新观察
├─ 栏目说明
├─ 1 条重点观察
└─ 2—4 条紧凑观察

核心作品
├─ 栏目说明
├─ Robotaxi
└─ 企业经营体系与数字化认知框架

关于我入口
└─ 简短定位 + 查看完整介绍

当前关注 / 最近更新
└─ 降为页面后部的一条状态信息
```

### 5.2 首屏合同

首屏只保留：

1. `xingbuild` 与作者关系；
2. 持续观察的范围；
3. 持续设计和构建的对象；
4. 进入最新观察的自然视觉路径。

以下内容退出首屏主要视觉区域：

- 所在地；
- 多项作品状态；
- 详细更新说明；
- 简历式能力罗列；
- 对 `xingbuild` 名称内在含义的公开解释。

首屏核心陈述最多两行，补充说明最多两行。中文桌面正文有效行宽控制在约 22—30 个汉字，避免横跨十二列。

### 5.3 最新观察

第 1 条为重点观察：

```text
日期 / 内容形态 / 主题
标题
一到两行摘要
```

其余观察使用紧凑行：

```text
日期        主题        标题                 一行摘要（空间允许时）
```

重点不是制造视觉卡片，而是用字号、间距和列关系形成优先级。

### 5.4 核心作品

每个作品先回答：

1. 解决什么问题；
2. 构建了什么；
3. 当前是什么状态；
4. 有什么证据边界；
5. 再展示简化架构关系。

架构图是作品说明，不作为首页第一视觉。首页只显示简化图或关系摘要，完整架构进入作品详情。

## 6. 观察列表

### 6.1 栏目开头

```text
观察
关于 Robotaxi、企业经营与数字化的持续观察和阶段性判断。
```

说明文字只定义范围，不使用“资讯”“新闻”或媒体化口号。

### 6.2 内容形态

第一阶段只在内容对象内部稳定使用：

- `brief`：短观察，聚焦一个事实、变化、问题或核心判断；
- `analysis`：分析文章，围绕完整问题展开因果链和结论。

现有其他格式只有在存在真实内容和独立阅读价值时保留。格式不升级为一级导航。

### 6.3 桌面列表

- 按年份分组；
- 使用日期、主题、标题和可选摘要的稳定列；
- 最新或置顶内容显示摘要；
- 普通归档默认不超过一行摘要；
- 整行可点击，并保持清楚的键盘焦点；
- 不使用每篇一张大卡片。

### 6.4 手机列表

每项改为两层：

```text
日期 · 主题 · 内容形态
标题
一行摘要（重点内容显示）
```

- 年份仍是清楚的分组标题；
- 不保留桌面表格式对齐；
- 标题优先于摘要；
- 点击区域覆盖整项，但链接语义仍然可识别。

### 6.5 暂缓能力

以下能力保留字段或演进位置，本轮不实现：

- 全文搜索；
- 复杂主题筛选；
- 多条件过滤；
- 花园式成熟阶段；
- Build Log；
- 自动发布到微信公众号和 X。

当观察达到约 20—30 篇或真实浏览已经困难时，再评估主题筛选。

## 7. 观察正文

### 7.1 正文前阅读契约

正文页按以下顺序呈现：

```text
返回观察
内容形态 / 主题
标题
一句话摘要
发布日期 / 更新日期
本文讨论的问题（长文可用）
目录（长文可用）
正文
```

- `brief` 不显示目录和额外导读卡。
- `analysis` 在存在两个以上二级章节时显示目录。
- “本文讨论的问题”只有在它能减少理解成本时出现，不要求每篇文章填充。

### 7.2 桌面正文

- 标题和摘要使用受控宽度，不横跨全屏；
- 正文主体控制在约 680—760px；
- 目录位于正文左侧，滚动时可保持可见；
- 目录不是第二套导航，不遮挡全站页头；
- 架构图可以突破正文宽度，但必须保留清楚的对象和关系。

### 7.3 手机正文

- 标题按中文语义自然换行，不使用桌面字号直接缩小；
- 元数据允许换行，不横向滚动；
- 目录折叠为“本文目录”，默认收起；
- 导读和正文保持单列；
- 表格优先改为分组条目；只有数据必须横向比较时允许局部横向滚动；
- 架构图切换为纵向关系，不缩成不可读的桌面图。

### 7.4 正文之后

按存在性显示：

1. 关联作品；
2. 延伸观察；
3. 内容更新时间或版本说明。

不显示空区块，不为了完整形式制造无内容模块。

## 8. 作品与关于我的必要适配

### 8.1 作品

作品列表和详情统一优先级：

```text
问题 → 构建对象 → 当前状态 → 结果或证据 → 架构与实现 → 局限
```

- 首页作品摘要不承担完整案例说明；
- 作品详情保留直接的业务架构图；
- Robotaxi 与企业经营体系和数字化认知框架保持两个独立作品；
- 不把关联观察替代作品的事实、状态与证据。

### 8.2 关于我

页面顺序调整为：

```text
简短定位
能够解决的问题
核心能力
代表项目成果
职业经历
简历
当前方向与联系方式
```

桌面保留左侧页内目录，手机改为正文前的单列目录。页面是证据导向的作者说明，不改造成在线简历。

## 9. 视觉与组件规则

### 9.1 保持

- 暖白底、墨色正文、赭色强调；
- 编辑型衬线标题；
- 精确线条、日期、编号和版本信息；
- 直接的业务架构图；
- 内容、表现和视觉令牌分离。

### 9.2 调整

- 降低首页首屏高度；
- 为栏目说明建立统一的 `section-intro` 层级；
- 建立重点观察与紧凑观察两种列表密度；
- 建立正文标题、摘要、元数据、导读、目录和正文的稳定层级；
- 同一组件通过响应式变体重组，不维护桌面和手机两套内容。

### 9.3 不采用

- 图形 Logo；
- 手绘、植物、花园、生长阶段和装饰性插画；
- 全站大卡片；
- 过多内容类型；
- 重型 CMS；
- 为模仿参考网站而改变 xingbuild 的品牌色彩和业务图表达。

## 10. 内容与工程边界

### 10.1 内容对象

观察对象至少支持：

```text
id
slug
title
summary
body
format
topics
status
publishedAt
updatedAt
relatedWorks
```

如果当前字段已经覆盖，不为命名一致而机械迁移。Engineering task 必须先分析现有字段、组件和路由差异，再决定最小变更。

### 10.2 表现组件

建议责任边界：

```text
SiteHeader
SectionIntro
ObservationFeature
ObservationRow
ObservationMeta
ArticleHeader
ArticleToc
RelatedContent
WorkSummary
```

组件只处理呈现和交互，不复制内容判断或作品状态规则。

### 10.3 视觉令牌

颜色、字体、正文宽度、页面边距、区块间距、边框和断点继续集中管理。不要在新组件中散落同义硬编码。

## 11. 验收场景

### 11.1 首页

- 桌面 1440px：首屏能同时看到定位和最新观察区的开始。
- 手机 390px：首屏不被作者状态信息占满，向下自然进入最新观察。
- 导航、重点观察、普通观察、作品和 About 入口均可操作。

### 11.2 观察列表

- 桌面能明显区分年份、重点内容和普通归档。
- 手机没有横向溢出，标题不被元数据压缩。
- 空摘要、无更新日期和不同内容形态不会破坏列表。

### 11.3 观察正文

- 短观察不出现空目录或空导读。
- 长文桌面目录可用，正文宽度适合连续阅读。
- 长文手机目录可展开和收起。
- 键盘可以到达导航、目录和正文链接，焦点可见。
- 正文、表格和架构图在 390px 不产生整页横向滚动。

### 11.4 回归

- `观察 / 作品 / 关于我` 路由继续有效；
- Robotaxi 与企业经营框架的状态和证据边界未被改写；
- 桌面与手机使用同一品牌色彩；
- 没有增加新一级栏目、CMS、搜索、自动分发或 Build Log；
- `npm run release:check` 全部通过；
- 使用真实浏览器完成桌面 1440px 与手机 390px 核心页面验证。

Engineering 网站迭代 task 接手后直接执行，不再等待本轮产品确认，但必须按顺序：

1. 读取 `AGENTS.md`、迭代发布规则、本方案和当前实现。

5. 保持内容对象、页面投影、视觉令牌和服务边界分离。
6. 完成构建、测试、桌面与手机真实页面验证。

8. 验证稳定后按项目规则创建本地提交和 `v0.3.0` 标签。
9. 不推送 GitHub、不发布 EdgeOne、不修改域名。
