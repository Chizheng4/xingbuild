# xingbuild v0.10.0 观察内容发布流水线方案

## 1. 结论

本轮只建设一次“内容发布能力”，不建设通用后台，也不把 Scheduled task 直接连接到生产环境。

网站以后明确分为两条通道：

```text
产品通道：结构 / 视觉 / 组件 / 工程变化
→ 版本迭代 → 完整验证 → commit + tag → 版本发布

内容通道：新增或修订一篇观察
→ 结构化候选 → 人工核验 → 本地草稿预览
→ 内容提交 → 内容专项验证 → content-only 发布
```

一篇观察不再触发版本号、tag、设计方案和全站专业验收。只有内容模型、页面结构、共享卡片、视觉 token 或发布能力本身发生变化时，才进入产品通道。

## 2. 当前问题与工程事实

### 2.1 当前内容与代码耦合

观察内容集中在 `src/content/siteContent.js`。新增文章必须编辑 JavaScript，并与网站工程修改混在同一个文件中，Scheduled task 产出的结构化候选不能直接进入稳定的内容入口。

### 2.2 当前生产发布只支持版本发布

`publish-xingbuild.command` 要求：

- 工作树干净；
- 当前分支为 `main`；
- `HEAD` 必须存在与 `package.json` 版本完全一致的 tag；
- 推送 tag 和 `main` 后再部署 EdgeOne；
- 公网版本、commit 与本地一致。

这些约束适合产品版本，但意味着每发布一篇内容都必须制造新版本和 tag。

### 2.3 当前运行环境不适合立即建设后台

当前 `.openai/hosting.json` 没有数据库和对象存储，`worker/index.js` 只承担静态资源与 SPA fallback。现在增加数据库、管理后台、登录、权限、备份和运行服务，会显著提高安全与维护成本，超过单作者网站当前需要。

因此 v0.10.0 采用 Git 内容库和受控命令；未来内容量、编辑人数或移动审阅需求达到阈值后，再迁移 Headless CMS 或内容 API。

## 3. 责任边界

### 3.1 Scheduled task

负责：

- 搜索、去重和结构化候选；
- 公司、地区、六个经营维度和事件时间归类；
- 区分事实、公司表述、媒体报道、观点和推断；
- 保留来源与冲突；
- 推荐精简、标准或深度层级。

不负责：

- 修改 xingbuild；
- 生成最终作者表达；
- 直接提交、推送或发布；
- 把推断写成经营事实。

### 3.2 内容发布 task

负责：

- 接收一个结构化 candidate；
- 打开来源完成事实核验；
- 形成 xingbuild 标题、摘要和详情正文；
- 生成本地草稿；
- 执行内容检查和本地预览；
- 在用户批准后提升为 published；
- 执行 content-only commit；
- 只有用户明确授权生产发布时，才推送、部署和公网验证。

### 3.3 Engineering task

负责一次性建设和维护：

- 内容目录、schema、读取器；
- candidate 导入和内容校验命令；
- 草稿预览与发布状态；
- content-only 提交范围检查；
- 独立内容发布脚本；
- 自动测试和项目规则。

Engineering 不负责日常文章编辑。

## 4. 内容对象

### 4.1 三层对象

```text
ObservationPublication
└─ EvidenceUnit × N
   └─ SourceRef × N → Source
```

- `ObservationPublication`：一次公开发布及其页面投影。
- `EvidenceUnit`：可以单独核验的事实、表述、观点或推断。
- `Source`：支持 EvidenceUnit 的外部来源。

发布深度、经营维度、主张性质、来源等级必须是四组独立字段。

### 4.2 ObservationPublication

```text
id
slug
status: draft | published
level: brief | standard | deep
nature: evidence-led | opinion-led

title
summary

companies[]
regions[]
dimensions[]
primaryDimension

eventAt?
periodStart?
periodEnd?
publishedAt?
updatedAt?

evidenceUnits[]
sources[]
sections[]
relatedWorks[]
promoteToHome
```

六个受控经营维度：

1. 准入与政策
2. 运营与市场
3. 安全与事件
4. 产品与能力
5. 合作与扩张
6. 经营与资本

“观点”不是经营维度；它属于 `nature` 或 EvidenceUnit 的 `claimKind`。

### 4.3 EvidenceUnit

```text
id
claimText
claimKind:
  verified_fact
  company_statement
  media_report
  opinion
  inference
sourceRefs[]
operatingImpact?
```

`operatingImpact` 是作者分析，不得拼入 `claimText` 后伪装成事实。没有来源的推断可以保留为作者判断，但必须明确标记，且不能成为精简观察的唯一主体。

### 4.4 Source

```text
id
publisher
title
url
publishedAt
sourceTier
sourceType
accessedAt
```

来源优先级：

```text
监管机构 / 政府 / 公司原始信息
→ 财报与公告
→ 可靠媒体
→ 公司负责人、行业专家的 X 原帖
```

来源等级不等于主张真实性。例如公司公告是原始来源，但公告中的预测仍是公司表述。

## 5. 内容目录与读取边界

推荐结构：

```text
content/
├─ schema/
│  └─ observation.schema.json
└─ observations/
   └─ {slug}.json

.content-workspace/
├─ candidates/
└─ imports/
```

- `content/observations/` 是公开观察的唯一版本化事实源，一篇观察一个 JSON 文件。
- `status=draft` 的文件可以通过本地直接链接预览，但不得进入观察索引、首页或生产构建。
- `.content-workspace/` 用于候选和临时导入，必须被 Git 忽略，不作为长期事实源。
- 现有两篇观察从 `siteContent.js` 无损迁移；作品与个人资料继续留在当前内容层，本轮不扩大迁移范围。
- 页面继续消费统一 `observations` 集合，不直接读取 Scheduled task 输出。

## 6. 三种发布层级与页面投影

### 6.1 共享卡片

精简、标准和深度全部沿用 v0.9.0 的 `ObservationCard`：

```text
Title
Summary
Metadata
```

保持：

- 一个整体原生链接；
- 同一 surface、border、radius、padding；
- 同一 hover、focus-visible、active；
- 同一桌面两列和手机单列；
- 首页、观察页、作品关联观察使用同一 DOM。

卡片 Metadata 最多显示：

```text
层级或观点 · 公司/地区 scopeLabel · 主维度 · 发布时间
```

来源和逐条主张性质进入详情页，不塞入卡片。

### 6.2 共同详情骨架

```text
Header
├─ Meta
├─ Title
└─ Summary

Body
├─ 范围与事实
├─ 经营影响
├─ 层级扩展内容
└─ 证据与边界
```

- 精简：事实概览、一个核心事件、经营影响、来源；无目录，不凑段落。
- 标准：增加周期内变化、公司或地区比较、趋势和关键不确定性。
- 深度：增加问题、因果链、商业化判断和关键不确定性；章节超过现有门槛时才显示目录。

视觉只新增三种受控角色：

1. 紧凑事实概览；
2. 非默认主张性质标签；
3. 可逐条追溯的来源列表。

不重做卡片品牌，不增加另一套观察页面视觉。

## 7. 首页与索引规则

### 7.1 观察索引

- 默认按 `publishedAt` 倒序；
- 所有层级使用同一 CardGrid；
- 第一版不增加筛选、分页和搜索；
- 内容量达到明确阈值后，再增加层级和六维度筛选；
- 不恢复年份 rail，不创建“精简区 / 标准区 / 深度区”三套模板。

### 7.2 首页

当前“最新四条”在高频精简内容出现后会退化为资讯 feed，应改为受控投影：

- 首页最多四条观察；
- 最多两条精简；
- 有已发布标准或深度内容时，至少保留一条；
- `promoteToHome=false` 的高频事件只进入观察索引；
- 首页选择规则必须集中在内容查询层，页面不得自行复制筛选逻辑。

## 8. 内容命令

建议提供稳定、可由 task 调用的命令：

```text
npm run content:import -- --input <candidate.json>
npm run content:check
npm run content:preview -- --slug <slug>
npm run content:promote -- --slug <slug>
npm run content:scope-check
```

责任：

- `content:import`：把 Scheduled candidate 转为本地 draft 骨架；不虚构缺失字段。
- `content:check`：校验 schema、枚举、slug、日期、sourceRefs、来源 URL、重复 ID 和发布门槛。
- `content:preview`：输出本地预览地址；不改变 published 状态。
- `content:promote`：在明确批准后将一个通过检查的 draft 提升为 published。
- `content:scope-check`：确认内容提交只修改允许的观察内容文件和必要生成索引。

命令失败必须保持原状态，不能留下半发布内容。

## 9. 独立内容发布通道

保留 `publish-xingbuild.command` 原有版本发布语义，不降低其 tag 和版本检查。

新增独立 `publish-content.command`，只允许已批准的 content-only commit：

1. 当前分支为 `main`；
2. 工作树干净；
3. 最近提交通过 content scope 检查；
4. `package.json` 版本未变化；
5. 不允许修改 src 组件、样式、worker、发布配置和设计规则；
6. 执行 `content:check`、生产 build、Sites 测试和必要 smoke test；
7. 推送 `main`，不创建或推送新 tag；
8. 部署现有 EdgeOne 项目；
9. 使用当前稳定版本号和新的 commit 校验公网；
10. 验证目标文章 URL、观察索引和首页投影。

`release.json` 可以保持当前稳定产品版本号，但 commit 必须反映最新内容提交。这样能够同时回答：

- 当前网站产品能力版本是什么；
- 当前线上内容对应哪个 commit。

脚本存在不代表获得发布授权。任何 push、EdgeOne 部署或公网发布，仍需用户在当前 task 明确批准。

## 10. 两级审核策略

### 10.1 可在未来自动发布的候选

仅限精简观察，并同时满足：

- 监管、政府、财报或公司正式公告等高优先级来源；
- 单一事实明确；
- 无来源冲突；
- 不涉及责任归因；
- 经营影响使用克制且明确标记的判断；
- 所有 schema 和内容门槛自动通过。

v0.10.0 只建立能力，不默认开启无人审核自动发布。

### 10.2 必须人工批准

- 标准和深度内容；
- 观点；
- 安全事故、责任和监管调查；
- 收入、成本、融资和单位经济性判断；
- 多来源冲突；
- 任何低置信度推断。

## 11. 一次内容发布的标准流程

```text
Scheduled task 输出 candidate
→ 内容 task 选中一个 candidate
→ 打开并核验来源
→ content:import
→ 完成作者表达
→ content:check
→ 本地详情页与索引预览
→ 用户批准
→ content:promote
→ content-only commit
→ 用户明确授权生产发布
→ publish-content.command
→ 公网文章、索引、首页与 release.json 验证
```

内容 task 的最终报告只需要：

- 发布了哪一篇；
- 使用了哪些核心来源；
- 事实、观点和推断边界；
- commit；
- 本地或公网 URL；
- 是否推送、部署以及公网验证结果。

## 12. Engineering 实施范围

### 必须完成

1. 建立独立内容目录和 schema。
2. 无损迁移现有两篇观察。
3. 内容读取器替代 `siteContent.js` 中的观察内联数组。
4. 扩展精简、标准和深度内容模型。
5. 保持 v0.9.0 共享卡片唯一性。
6. 建立详情页事实概览、主张性质和来源投影。
7. 建立候选导入、校验、预览、提升和 scope 检查命令。
8. 建立独立 content-only 发布脚本，同时保持版本发布脚本原样有效。
9. 建立首页配额规则。
10. 增加 schema、来源引用、状态隔离、首页配额和发布范围测试。
11. 更新项目规则，明确产品版本与内容发布的区别。
12. 对桌面和手机进行真实浏览器验证。

### 明确不做

- 不建设登录和后台 UI；
- 不引入数据库、R2 或第三方 CMS；
- 不让 Scheduled task 直接写生产；
- 不默认开启无人审核发布；
- 不修改导航；
- 不重做 v0.9.0 卡片视觉；
- 不修改作品、About 和企业架构；
- 不推送、不发布、不修改 DNS。

## 13. 验收门槛

### 内容模型

- 现有两篇观察迁移后标题、摘要、正文、关联作品和证据边界不丢失；
- 六个维度、三种层级和五种 claimKind 为受控枚举；
- 每个 EvidenceUnit 的 sourceRefs 都能解析；
- draft 不进入任何公开集合。

### 页面

- 首页、观察页和作品关联区继续使用同一 ObservationCard；
- 卡片仍只有一个整体链接，顺序保持 Title → Summary → Metadata；
- 精简详情在手机首屏后可以快速看到事实和经营影响；
- 标准、深度保持阅读宽度和目录门槛；
- 来源可以逐条访问；
- 没有横向溢出和中文词组异常拆分。

### 流程

- 一条有效 candidate 可以进入 draft 并通过本地直接 URL 预览；
- 缺来源、错误枚举、悬空 sourceRefs、重复 slug 和推断冒充事实会被拒绝；
- 提升前后公开集合状态正确；
- content scope 检查会拒绝混入工程代码的提交；
- 产品版本发布脚本仍要求 matching tag；
- 内容发布脚本不要求新 tag，但能够验证稳定版本号和内容 commit。

### 真实浏览器

一次性实施验收覆盖：

- 1440、1024、768、557、520、390、320；
- 首页、观察索引、精简详情、标准/深度详情；
- 卡片、来源链接、目录、移动导航和无横向滚动；
- v0.8.0 企业架构和 v0.9.0 作品/About 回归。

日常内容发布只做内容专项自动检查、目标详情页桌面/手机 smoke test 和公网目标 URL 验证，不重复完整七档专业验收。

## 14. 首次流程验证

v0.10.0 Engineering 完成并通过专业验收后：

1. Scheduled task 按新合同搜索 2026 年 7 月 Robotaxi 信息；
2. 输出多条独立 candidates，不预先合并成一篇；
3. 用户选择其中一条；
4. 内容 task 完成来源核验、导入、作者表达和本地预览；
5. 先验证 draft、卡片、详情和内容门槛；
6. 只有用户再次明确批准时，才执行 content-only commit 和生产发布；
7. 复盘总耗时、人工步骤、失败点和是否适合进一步自动化。

本次验证的目标不是快速增加文章数量，而是证明“Scheduled candidate → 可核验草稿 → 统一页面投影 → 受控发布”形成稳定闭环。
