# v0.8.0 单页交互式企业认知架构方案

## 1. 结论

`v0.7.0` 将企业认知框架实现为需要进入、切换视图、下钻概念和返回的“认知框架浏览器”。真实页面验证表明，这种结构把产品方法、学习路径和来源说明放在了知识价值之前，用户需要经过过多阅读和跳转，才能看到真正的企业经营架构。

`v0.8.0` 将产品重新定义为：

> 一张可以从上到下直接阅读的网页，用四个核心问题和四张交互式架构图，直接呈现企业经营体系的关键知识。

固定体验：

- 页面标题直接使用“认知企业经营体系”；
- 标题之后马上展示第一张整体架构图；
- 每张架构图只有一个核心问题、一句说明和完整架构；
- 桌面点击节点后，左侧保留完整架构图，右侧显示解释；
- 手机从上到下直接展示四张架构图，点击解释出现在当前架构下方；
- 悬停和键盘聚焦只提示“这个节点可以点击”，不承担知识解释；
- 不再使用入口页、视图切换、学习路径、面包屑或独立概念页作为主要体验。

---

## 2. 本轮设计目标

### 2.1 用户任务

访问者打开页面后，应当立即完成三件事：

1. 看见企业经营体系的整体关系；
2. 选择架构节点并理解其含义和作用；
3. 继续向下阅读其他架构，不需要学习如何使用网站。

### 2.2 产品成功的根本判断

不是读者是否理解“这套认知框架如何构建”，而是：

- 是否立即看到关键架构；
- 是否理解节点之间的关系；
- 是否能用很少的操作获得概念解释；
- 是否能在一张网页中看完核心知识。

### 2.3 公开内容边界

页面不展示：

- 构建逻辑；
- 学习路径；
- 证据边界；
- 当前状态；
- 上游事实源；
- career 项目说明；
- 框架版本和同步关系；
- “如何阅读”说明；
- 独立的“进入认知框架”行动；
- 面向项目维护者的内容治理说明。

这些内容继续作为项目内部维护规则存在，但不占用访问者的阅读路径。

## 3. 页面结构

整页固定为五个连续内容段：

```text
页面标题与一句定位
        ↓
架构一：企业如何经营
        ↓
架构二：业务如何被设计
        ↓
架构三：数字化如何进入企业运作
        ↓
架构四：复杂业务概念如何获得明确含义
```

页面没有二级入口、Tab 切换、目录式学习步骤或独立概念路径。四张架构图在页面中全部真实存在，用户持续向下滚动即可看完。

### 3.1 页面标题

标题：

> 认知企业经营体系

一句定位：

> 用四张架构图，理解企业如何经营、设计业务、实现数字化，并用统一概念表达复杂现实。

标题区之后直接进入第一张架构图，不增加作品类型、框架状态、版本、来源、阅读说明或长篇问题陈述。

---

## 4. 四个核心问题与架构图

### 4.1 架构一：企业如何经营

核心问题：

> 一家企业如何持续创造价值、形成经营结果并调整自身？

一句说明：

> 企业在外部环境和利益相关者需求下作出选择，组织现实运作，并根据事实与结果持续调整。

架构类型：

- 企业经营体系整体关系图；
- 以经营反馈闭环为主要视觉结构；
- 同时显示企业现实、经营与架构设计、数字化实现和运行反馈；
- 第一眼能够识别“现实—设计—实现—运作—事实与结果—反馈”的循环关系。

主要节点：

- 外部环境、利益相关者与需求；
- 企业经营体系；
- 经营与架构设计；
- 数字化实现；
- 企业运作；
- 事实与经营结果；
- 运行反馈。

这张图承担整体认知，不再另外提供“总览”页面。

### 4.2 架构二：业务如何被设计

核心问题：

> 如何把战略和经营目标转化为可执行、可度量的业务设计？

一句说明：

> 企业业务架构从多个固定视角设计同一企业现实，使能力、责任、流程、对象、规则和指标相互一致。

架构类型：

- 企业业务架构关系图；
- 以价值如何形成并被组织执行为主线；
- 不把九个视角展示成无关系的概念清单。

首版主要节点：

- 利益相关者需求或业务事件；
- 价值流；
- 企业能力与资源；
- 企业职能与组织责任；
- 业务流程；
- 业务对象与事件；
- 业务规则；
- 事实与结果；
- 业务指标；
- 经营目标差距。

关系线必须表达“触发、需要、承担、执行、约束、改变、产生、衡量”等语义。

### 4.3 架构三：数字化如何进入企业运作

核心问题：

> 如何把业务设计转化为真正进入企业运作的产品、数据和系统？

一句说明：

> 企业业务架构提出数字化需求，产品、数据、技术和工程共同形成进入企业现实的数字化系统。

架构类型：

- 数字化实现链路图；
- 以从业务设计到现实运行的转化顺序为主；
- 表达并行关系、共同驱动和最终进入企业运作。

主要节点：

- 企业业务架构；
- 数字化需求；
- B 端产品架构；
- 数据架构；
- 技术架构；
- 工程实现；
- 企业数字化系统；
- 企业现实；
- 企业运作；
- 事实与经营结果。

### 4.4 架构四：复杂业务概念如何获得明确含义

核心问题：

> 如何避免同一个业务词在不同讨论中混用，失去明确边界？

一句说明：

> 具体业务概念通过十类底层性质获得确定含义，使对象、变化、规则、事实、指标和结果能够被一致表达。

架构类型：

- 底层概念关系图；
- 以“现实参与—现实结构—现实变化—现实约束—证据与判断”为阅读分组；
- 表达底层概念之间的作用和判断关系，不做词典式平铺。

主要节点：

- 主体；
- 对象；
- 关系；
- 状态；
- 事件；
- 活动与过程；
- 规则；
- 事实；
- 指标；
- 结果。

运行反馈已经包含在第一张整体架构中，不再单独增加第五张架构图。

## 5. 单张架构图的固定构成

每张架构图只有四个内容对象：

```text
核心问题
一句说明
交互式完整架构图
节点解释区
```

不增加：

- 当前视图；
- 架构切换 Tab；
- 阅读提示；
- 概念路径；
- 查看完整定义；
- 来源与版本卡片；
- 相关观察；
- 下一步学习入口。

### 5.1 默认状态

- 架构图完整可见；
- 默认选中最能代表该架构主题的中心节点；
- 解释区直接显示该节点说明，避免空白面板；
- 用户不操作也能从架构名称、节点和连线理解主要关系。

### 5.2 节点解释内容

点击节点后的解释只保留：

1. 概念名称；
2. 一段简明定义；
3. 它在当前架构中的作用；
4. 与当前直接相连节点的关系。

默认不显示概念性质、来源、版本、依赖列表、上层结构和边界辨析。只有删除后会导致当前概念被误解时，才允许增加一句必要辨析。

## 6. 交互合同

### 6.1 悬停与聚焦

悬停和键盘聚焦的唯一任务是提示可点击：

- 节点轻微上浮 `2–4px`；
- 节点边界或侧边强调从中性色切换为赭色；
- 与节点直接相连的关系线提高对比度；
- 鼠标显示可点击状态；
- 动画约 `140–200ms`，快速、克制；
- 不弹出承载长文字的 tooltip。

悬停离开后恢复，不改变当前选中节点。

### 6.2 点击

点击后：

- 节点保持选中状态；
- 相关连接线和直接相邻节点获得关系高亮；
- 解释区更新为当前节点内容；
- 不跳转页面；
- 不改变架构图位置；
- URL 可以保留轻量状态，但不能要求读者理解路由；
- 再次点击其他节点，只替换当前解释。

### 6.3 桌面

每个架构段采用：

```text
核心问题与一句说明
┌──────────────────────┬───────────────┐
│ 完整架构图 约 62–68% │ 解释区 32–38% │
└──────────────────────┴───────────────┘
```

- 左侧架构始终完整存在；
- 右侧解释区可以在当前架构段内保持可见；
- 不把页面长期固定成全局左右双栏；
- 四个架构段仍然从上到下连续阅读；
- 解释区不得遮挡或压缩主要关系；
- 架构图不允许自由拖拽、编辑节点或无限缩放。

### 6.4 手机

手机保持四张架构全部直接展示：

```text
核心问题
一句说明
纵向重排的完整架构图
当前节点解释
```

- 不使用 Tab、折叠、轮播或横向分页；
- 不把桌面架构等比缩小；
- 节点和关系按语义改为纵向排列；
- 点击节点后，解释显示在当前架构图下方；
- 选择节点不跳转独立页面；
- 用户继续向下滚动即可阅读下一张架构；
- 390px 和 320px 都必须看清节点名称、关系标签和点击状态。

### 6.5 可访问性

- 所有节点使用真实 `button` 或等价可聚焦语义；
- hover 状态必须同时具有 `focus-visible` 状态；
- 当前节点使用 `aria-pressed` 或等价选中语义；
- 当前关系不能只依靠颜色区分，应同时使用线宽、线型或节点边界；
- 解释区更新需要具有可感知的标题结构；
- 尊重 `prefers-reduced-motion`；
- 不用只在 hover 出现的重要知识内容。

## 7. 外部优秀机制研究

本轮只学习外部产品解决问题的机制，不复制其品牌。

### 7.1 IBM Technical Diagrams

参考：

- [IBM Design Language — Technical diagrams](https://www.ibm.com/design/language/infographics/technical-diagrams/design/)

可继承机制：

- 用节点和连接线表达结构、层级与顺序；
- 节点、连接点和内容对齐到稳定网格；
- 连接线优先使用清晰、可追踪的正交路径；
- 线条颜色差异必须同时配合标签或线型；
- 节点尺寸、边距和连接方式形成一致系统。

不复制：

- IBM 蓝色；
- IBM Plex 字体；
- Carbon 组件外观；
- 技术基础设施图的冷色和高密度表现。

xingbuild 转化：

- 使用现有暖白、墨色、赭色和 Noto Serif/Sans SC；
- 赭色只表达当前节点、可点击状态和当前关系；
- 线条属于真实架构关系，可以使用必要边界，但不扩散为全站卡片语言。

### 7.2 React Flow

参考：

- [React Flow examples](https://reactflow.dev/examples)
- [React Flow component API](https://reactflow.dev/api-reference/react-flow)

可继承机制：

- 节点点击事件与选中状态；
- 自定义节点内容；
- 节点与外部详情面板联动；
- 水平、树状和自动布局思路；
- 触控设备上的明确点击目标。

当前不建议直接引入 React Flow：

- 当前产品不是流程编辑器；
- 用户不需要拖拽、连线、缩放、框选、工具栏或保存画布；
- 引入完整图编辑运行时会增加依赖、样式覆盖和移动端复杂度；
- 容易让页面呈现为软件工具，而不是 xingbuild 的编辑型知识作品。

只有未来出现动态节点数量、用户自由探索大型网络、复杂自动布局或编辑需求时，才重新评估 React Flow。

### 7.3 W3C Hover or Focus

参考：

- [W3C WAI — Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)

可继承机制：

- hover 不能成为获得知识的唯一方式；
- 临时浮层如果承载内容，需要可关闭、可悬停并保持稳定；
- 点击形成的稳定详情比多层 hover 浮层更可预测。

xingbuild 决策：

- hover 只表达可点击；
- 所有知识解释由点击后的稳定区域承载；
- 键盘聚焦获得同等提示；
- 手机不损失任何信息。

### 7.4 Observable 的响应式嵌入机制

参考：

- [Observable embeds](https://observablehq.github.io/documentation/embeds/)

可继承机制：

- 交互图形随内容容器响应，而不是固定画布尺寸；
- 图形与正文属于同一阅读流；
- 移动端重新组织图形，而不是简单缩放桌面画布。

不采用 Observable 嵌入运行时；本项目保留 React 内容组件和本地数据模型。

## 8. 技术方向

### 8.1 推荐实现

首版使用：

> React 状态管理＋语义 HTML 节点＋受控 SVG 连接线＋现有 CSS token。

责任划分：

- HTML `button`：节点文字、键盘焦点、选中状态；
- SVG：连接线、箭头、关系标签和当前关系高亮；
- CSS Grid：桌面左图右解释；
- 普通文档流：四个架构段的纵向阅读；
- React state：当前选中节点；
- 现有 `frameworkModel.js`：概念与关系的单一内容模型；
- CSS media query：桌面架构与手机纵向投影。

### 8.2 为什么不是一张图片

- 节点需要真实点击和键盘语义；
- 解释需要根据选择更新；
- 手机需要重新排列；
- 文字需要清晰缩放和语义断行；
- 关系状态需要实时高亮。

效果图只能作为视觉来源，不能成为最终页面中的架构图片。

### 8.3 为什么首版不使用 React Flow、D3 或 Canvas

- 四张图的节点和关系数量有限且稳定；
- 不需要自动编辑、拖拽或复杂力导向布局；
- HTML＋SVG 更容易继承现有品牌和排版；
- 更容易实现手机语义重排；
- 更容易测试节点名称、关系标签、键盘状态和解释更新；
- 依赖更少，维护成本更低。

升级条件：

- 单图节点超过当前静态布局能够清晰承载的规模；
- 关系根据数据动态变化；
- 需要用户缩放、平移、过滤、展开或编辑；
- 多种架构需要共用自动布局引擎；
- HTML＋SVG 的布局维护成本被真实证据证明过高。

## 9. 统一视觉保护

### 9.1 必须继承

- `xingbuild` 作为唯一页头身份；
- 暖白背景、墨色正文和赭色交互强调；
- 编辑型衬线标题与无衬线界面/图中文字；
- 现有页面 gutter、内容宽度和空间 token；
- 页面结构主要由排版、对齐和留白建立；
- 手机与桌面共享同一颜色语义；
- 节点编号只在数字真实表达顺序时使用。

### 9.2 架构图允许的专用表达

架构图属于真实关系表达，可以使用：

- 节点边界；
- 连接线和箭头；
- 必要的浅层分组背景；
- 当前节点状态；
- 当前关系线状态；
- 少量关系标签；
- 有明确意义的嵌套边界。

不得扩散为：

- 全站卡片化；
- 大量阴影；
- 多色分类系统；
- 霓虹、渐变或科技蓝；
- 仿 SaaS 控制台；
- 手绘、草图或装饰隐喻；
- 为视觉效果新增没有概念意义的节点和连线。

### 9.3 视觉判断优先级

```text
关系是否正确
    ↓
整体是否一眼可读
    ↓
当前节点与关系是否明确
    ↓
文字是否足够少
    ↓
是否保持 xingbuild 品牌
    ↓
动效是否克制自然
```

## 10. 结构视觉 task 交付要求

结构视觉 task 读取本方案后，负责深入设计展示视觉，不直接进入 Engineering。

必须交付：

1. 1440px 页面整体效果图，能够看到标题和至少第一张完整架构；
2. 1440px 节点点击状态效果图，明确左图右解释；
3. 390px 手机整页结构效果图，证明四张架构从上到下直接阅读；
4. 390px 手机节点点击状态效果图；
5. 节点默认、hover/focus、selected 三种状态规范；
6. 连接线默认、相关、当前三种状态规范；
7. 四张架构图各自的构图草图或明确布局；
8. 外部参考机制与 xingbuild 视觉转化说明；
9. 尚未证实的视觉或技术假设。

工作原则：

- 以一个推荐方向深入，不制作多套完整产品方案；
- 可以对局部构图比较少量选项，但必须给出明确推荐；
- 使用当前页面和本方案作为内容来源；
- 效果图必须使用真实中文节点名称和真实一句说明；
- 不用占位文字；

## 12. 验收标准

### 12.1 首屏

- 页面标题是“认知企业经营体系”；
- 一句定位之后立即出现第一张架构；
- 1440px 能看到第一张架构的主体关系；
- 不先展示产品方法、来源或学习说明。

### 12.2 架构

- 四个核心问题分别对应四张架构；
- 架构通过位置和连线表达关系，不是概念列表；
- 每条必要关系具有可理解的方向或文字；
- 默认状态也能理解主要关系；
- 点击后当前节点和直接关系明显。

### 12.3 互动

- hover/focus 明确提示可点击；
- 点击不离开当前架构；
- 桌面左图保持完整，右侧解释更新；
- 手机解释显示在当前图下方；
- 重要知识不依赖 hover；
- 动效克制且支持减少动态效果。

### 12.4 内容

- 每张架构只有一个问题和一句说明；
- 节点解释短、准确、与当前架构直接相关；
- 不公开展示构建逻辑、学习路径、证据边界、来源和 career；
- 内部仍然保留概念与关系的单一事实模型。

### 12.5 响应式与品牌

- 四张图在桌面与手机表达同一知识关系；
- 手机从上到下可以直接看完；
- 不增加 Tab、折叠或横向分页；
- 保持 xingbuild 的暖白、墨色、赭色和字体角色；
- 外部参考不改变品牌身份。
