# v0.24.27 内容发布状态机与幂等恢复方案

## 根因

独立内容发布的 transport、publicVerify、finalize 没有共享一个可恢复的不可变 release 状态。传播延迟会被误判为失败；重试会重复部署；finalize 仍读取旧 tracked 内容路径并删除生命周期证据，造成发布事实丢失。

## 唯一方案

```text
prepared → built → transported(deploymentId)
        → verifying(retryable, identity-bound)
        → finalized(atomic/idempotent) → released
```

所有阶段绑定同一 `contentReleaseId`、`contentHash`、`baseSiteArtifactId` 和 immutable package。失败只保留可恢复事实；同一 release 恢复时不重建内容、不重复 deployment。

## 实施范围

- 增加 release lease/幂等键和持久化状态，支持同一 package/deployment resume。
- publicVerify 支持有界等待与重试，并校验 content identity、base artifact、产品公网版本和目标路径。
- finalize 只读取独立 `.content-workspace/content` 与 release package；原子写入完成事实，保留 recovery、review、draft、package、log。
- 明确 `prepared/built/transported/verifying/finalized/released/failed/recoverable/rolled-back` 状态，禁止部署成功自动等于发布成功。
- 30 条 observations 串行发布时，单个目标失败不得污染其他目标或产品版本。

## 协作基线收口

- 活动 task 身份使用 `docs/rules/task-registry.md`；归档、重建、宿主或回传地址变化时更新。
- 与用户统一使用 Xing；复杂方案、架构、流程和收口文档图形优先。

## 非目标

不修改内容正文、来源、status、publishedAt、UI、IA、schema、路由、上游事实或已发布版本；不创建并行 task、branch、worktree 或 automation。

## 验收

- 公网传播延迟可在同一 release 上等待/重试并成功收口。
- transport 成功、finalize 中断后可恢复，不出现 publication file missing。
- 同一 release 重试不产生重复 deployment 或错误覆盖。
- 每个失败阶段保留完整 package/recovery/log，恢复后身份不变。
- 产品版本与内容发布完全独立，产品发布不携带内容身份。
