# v0.6.0 视觉结构与空间节奏系统方案

## 1. 方案结论

当前问题不是若干 margin 不够好看，而是空间系统只有数值尺度，没有完整的对象层级、邻接关系和责任归属。

`v0.6.0` 应建立可迁移的视觉结构与空间节奏系统：

```text
内容对象模型
→ 视觉层级
→ 邻接关系
→ 空间 token
→ 布局责任
→ 组件实现
→ 跨页面和跨模板验证
```

目标不是让 xingbuild 表面更像 Maggie，而是获得 Maggie 已经表现出的结构能力：同类对象具有稳定骨架，同级关系具有一致节奏，内容增加后页面仍能自然延伸。

## 3. 已知事实与判断

### 3.1 xingbuild 已有优势

- Page、Section、观察、作品等内容对象已经存在；
- 栏目编号、标题、说明、行动和内容能够被识别；
- 同类作品对象已经复用相同组件；
- 字体角色、颜色和版心稳定；
- v0.5.1 的中文语义换行已经在线上页面生效。

### 3.2 结构性问题

首页实测：

- 最新观察内容末端约在 1108px；
- 核心作品栏目内容起点约在 1364px；
- 两者实际视觉间隔约 256px；
- 形成原因是上一栏目尾部约 128px与下一栏目头部约 128px叠加。

同一页面内部同时存在：

- 栏目导语 → 第一项内容约 48px；
- 作品对象 → 下一作品对象约 64px；
- 多种对象内部关系反复使用 12–16px；
- 栏目边界突然扩大到约 256px。

因此当前节奏不是完全没有规律，而是：

```text
大层级：被两个组件重复拥有，过松
小层级：大量使用相同距离，关系分辨率不足
中层级：没有明确的语义组
```

### 3.3 Maggie 的机制

Maggie 的视觉友好来自重复结构，而不只是留白大小：

- `栏目标题 → 栏目说明 → 内容集合` 形成固定栏目骨架；
- 同类内容项反复使用 `标题 → 说明 → 元数据`；
- 同级栏目之间由父级 grid 的统一 gap 控制；
- 内容多少和标题行数变化时，结构关系仍然可预测；
- 紧密关系、对象关系和栏目关系具有可辨识层级。

不应直接复制 Maggie 的约 40px 栏目 gap、卡片、插画或英文密度。xingbuild 的中文编辑型方向可以更疏，但只能由一个责任方产生该距离。

## 4. 本轮要建立的框架

### 4.1 六层视觉结构

| 层级 | 对象 | 当前例子 | 责任 |
| --- | --- | --- | --- |
| L0 | Page Frame | 首页、观察页 | 版心、页面边缘、栏目流 |
| L1 | Section | 最新观察、核心作品 | 栏目边界和栏目内部结构 |
| L2 | Content Group | SectionIntro、重点观察、作品集合 | 同类内容分组 |
| L3 | Content Object | 一篇观察、一项作品 | 独立可复用内容单位 |
| L4 | Element | 序号、类型、标题、说明、状态、行动 | 信息角色 |
| L5 | Relationship | 标题→说明、对象→对象 | 间距语义 |

这一层级是未来更换布局和模板时需要继承的事实。网格和像素可以换，层级和关系不能丢。

### 4.2 标准栏目骨架

每个栏目统一为：

```text
Section
├─ SectionIntro
│  ├─ Identity：序号 / 类型
│  ├─ Heading：栏目标题
│  ├─ Description：栏目说明
│  └─ Action：进入栏目
└─ SectionBody
   ├─ Featured Object（可选）
   └─ Collection
      └─ Content Object × N
```

`Action` 可以与标题或说明在网格上并列，但在语义上仍属于 SectionIntro。页面不能为某一栏目临时创造另一套头部结构。

### 4.3 标准内容对象骨架

观察和作品的内容不同，但都应投影为四个语义组：

```text
Content Object
├─ Identity：序号、日期、类型、主题
├─ Proposition：标题、核心判断或问题
├─ Evidence：摘要、构建内容、状态、证据边界
└─ Action：继续阅读、进入作品
```

不是每个对象都必须显示四组，但显示出来的内容必须进入正确语义组。不同元素不能只因为都属于一张“卡片”就统一使用 16px。

## 5. 空间系统

### 5.1 关系优先

使用 Visual System v1 新增的：

- `bind`
- `relate`
- `object`
- `group`
- `section`

先判断相邻对象属于哪一种关系，再映射到当前主题的数值。

### 5.2 单一责任

本轮最重要的工程规则：

> 相邻间距只能由共同父级拥有。

具体要求：

- 首页 Page Stack 统一拥有 Section → Section 的距离；
- Section Flow 统一拥有 SectionIntro → SectionBody 的距离；
- Collection Flow 统一拥有 Content Object → Content Object 的距离；
- Object Stack 统一拥有对象内部语义组之间的距离；
- Element Relationship 只处理组内紧密元素。

Section 不再同时使用头尾 padding 制造相邻栏目距离。

### 5.3 当前主题的目标节奏

- Section → Section：桌面 96–128px，手机 64–88px；
- SectionIntro → SectionBody：桌面 40–48px，手机 32–40px；
- Content Object → Content Object：桌面 48–64px，手机 40–56px；
- 对象内部语义组：桌面 24–32px，手机 20–28px；
- 组内标题、说明、元数据：8–20px，按关系选择。

这些是目标区间，不是要求 Engineering 在组件中散落硬编码。

## 6. 页面调整

### 6.1 首页

- 消除相邻 Home Section 头尾空间叠加；
- 保持 Hero 当前构图，不再次缩短 Hero；
- 统一最新观察与核心作品的 SectionIntro 骨架；
- 把作品对象内部重组为 Identity、Proposition、Evidence；
- 保持 About 更简洁，但使用相同关系 token。

### 6.2 观察列表

- PageIntro、年份、重点观察、归档行形成明确四层；
- 年份不能承担大面积空白的替代作用；
- 重点观察与归档行的不同密度应由对象类型表达；
- 同类归档行增加后，间距必须自动保持一致。

### 6.3 作品、关于我与长文

- 不要求页面外观完全相同；
- 要求相同关系使用相同 token；
- 长文继续遵守段落、标题、列表和讨论提示的阅读节奏；
- 作品详情的事实、证据和边界按语义组组织，不按页面位置临时调间距。

## 7. 工程边界

推荐落点：

- 语义 rhythm token；
- PageStack、SectionFlow、CollectionFlow、ObjectStack 等最小布局原语，或现有组件的等价责任；
- SectionIntro 和内容对象内部语义组；
- 视觉合同测试与真实页面测量。

不要：

- 新建大量只包一层 `div` 的抽象组件；
- 把所有页面强行改成同一 DOM；
- 为达到截图效果加入页面专用 magic number；
- 使用装饰线、卡片和底色弥补对象关系不清；
- 在这一轮更换字体、颜色、品牌、导航或内容模型。

## 8. 验收方式

### 8.1 结构验收

- 每种关键页面能标出 L0–L5；
- 每一段主要垂直距离都能指出唯一责任方；
- 同类栏目和内容对象复用相同骨架；
- 内容增加一项时不需要新增页面 CSS；
- 删除可选说明或状态后，不产生异常空白。

### 8.2 视觉验收

桌面：1440、1024、768px。  
手机：557、520、390、320px。

逐对检查：

- Hero → 第一栏目；
- SectionIntro → 第一项内容；
- 重点对象 → 归档对象；
- 内容对象 → 下一内容对象；
- 标题 → 说明；
- 说明 → 状态或行动；
- 一个栏目 → 下一栏目。

不是只检查单个 margin 数值，而是截图并测量相邻对象的实际边界。

### 8.3 回归

- 中文语义换行不回退；
- 557px 行内导航和 520px 以下全屏菜单不回退；
- 无横向溢出；
- 无控制台 error/warning；
- `npm run release:check` 通过。

## 9. 版本与执行

本轮建议作为 `v0.6.0`，因为它新增的是可复用视觉结构能力，不是快速间距修订。

Engineering task 应先读取本方案与 Visual System v1，识别现有 DOM、组件和 CSS 中的实际责任，再给出一次文件级计划并直接实施。完成本地真实桌面与手机验收、release check、本地提交和 `v0.6.0` 标签后停止。

不推送、不发布，不修改域名。
