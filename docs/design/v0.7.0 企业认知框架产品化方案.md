# v0.7.0 企业认知框架产品化方案

## 1. 结论

企业认知框架不应被实现为一张承载全部概念的静态架构图，也不应依靠多层悬停浮层完成学习。它应被产品化为一个建立在唯一权威知识模型上的认知框架浏览器：

> 一个权威知识模型，提供总览、局部结构、概念定义、底层追溯和场景应用五种相互连接的阅读视图。

用户先通过企业经营体系总览形成整体认知，再按需要进入四个平面、具体结构和概念；当需要判断概念性质或边界时，继续追溯到十类底层基础概念；最后进入供应链、Robotaxi 和职业经历等应用。

交互采用：

- 悬停或键盘聚焦：快速预览；
- 点击：打开稳定的概念详情；
- 路径记录：保留当前认知上下文；
- 独立概念页：承载深度阅读、辨析和应用；
- 手机触控：使用抽屉或独立页面，不依赖悬停。

`v0.7.0` 先实现最小充分的探索闭环，用真实页面验证读者能否理解、下钻、追溯和返回；不建设自由画布、知识图谱编辑器、AI 问答或后台管理。

## 2. 问题定义

### 2.1 用户真正需要完成的任务

用户不是为了浏览一组术语，而是需要：

1. 从宏观理解企业如何经营、运作和数字化；
2. 看到某一局部在整体中的位置和上下游关系；
3. 理解某个概念的权威定义、性质、边界和直接依赖；
4. 从上层概念持续追溯到底层固定概念；
5. 将抽象认知映射到供应链、Robotaxi 和职业经历；
6. 在学习、复盘和对外讲解时沿同一框架使用，不形成多套定义。

### 2.2 当前文档形态的限制

`企业经营体系、数字化与职业定位认知框架 v5.1` 已经形成：

- 企业经营体系总览；
- 企业现实、经营与架构设计、数字化实现、运行反馈四个平面；
- 自上而下的学习顺序；
- 自下而上的知识构建和修订顺序；
- 十类底层基础概念；
- 企业业务架构固定视角；
- 供应链、Robotaxi 和职业定位应用。

当前主要问题不是概念缺失，而是文档阅读仍以章节为主要载体。读者可以线性阅读，但难以在总览、局部、概念定义、依赖关系和应用之间保持上下文并快速往返。

### 2.3 根本产品矛盾

```text
知识模型要求自下而上保持定义依赖正确
                    ↕
学习体验要求自上而下从整体逐层深入
```

解决方式不是维护两套内容，而是：

```text
唯一权威知识模型
      ↓
多种阅读投影
```

## 4. 产品结构

### 4.1 一个模型，五种视图

```text
企业经营体系总览
        ↓
四个平面与局部结构
        ↓
概念详情
        ↓
底层定义与依赖
        ↓
供应链 / Robotaxi / 职业经历应用
```

五种视图不是五套内容，而是对同一知识对象和关系的不同投影。

### 4.2 总览视图

总览负责回答：

- 企业经营体系整体是什么；
- 四个平面分别承担什么责任；
- 企业现实、设计、数字化实现和运行反馈如何连接；
- 读者可以从哪里继续深入。

总览只显示理解整体所需的最少节点和有明确含义的关系，不将全部概念压入一张图。

### 4.3 局部结构视图

局部视图负责展开四个平面中的具体关系，例如数字化实现：

```text
企业业务架构
      ↓ 提出数字化需求
B 端产品架构 ↔ 数据架构
      ↓ 共同驱动
技术架构
      ↓ 通过工程实现形成
企业数字化系统
      ↓ 进入企业现实并支持或执行
企业运作
```

进入局部后仍保留所属平面和上层总览位置，但降低非当前内容的视觉权重。

### 4.4 概念详情视图

每个核心概念使用同一详情结构：

| 内容 | 回答的问题 |
| --- | --- |
| 正式名称 | 当前研究的概念是什么 |
| 权威定义 | 它的固定含义是什么 |
| 概念性质 | 它本质上属于什么 |
| 所属平面 | 它位于企业现实、设计、数字化还是反馈 |
| 回答的问题 | 使用它是为了解决什么认知问题 |
| 直接依赖 | 理解它之前需要哪些概念 |
| 上层结构 | 它属于哪些结构或视图 |
| 相关概念 | 哪些概念与它相关但不是定义依赖 |
| 易混淆概念 | 它与相近概念的边界是什么 |
| 应用 | 它如何映射到具体业务和作品 |
| 来源与版本 | 当前定义来自哪里、何时同步 |

### 4.5 底层追溯视图

所有上层概念最终通过十类基础概念性质获得确定含义：

| 阅读分组 | 底层概念 |
| --- | --- |
| 现实参与 | 主体、对象 |
| 现实结构 | 关系、状态 |
| 现实变化 | 事件、活动与过程 |
| 现实约束 | 规则 |
| 证据与判断 | 事实、指标、结果 |

底层概念是共享依赖，不是为了页面结构重复复制到每个上层概念中。

### 4.6 应用视图

应用视图说明同一概念如何进入具体场景：

```text
权威概念
├─ 供应链应用
├─ Robotaxi 应用
└─ 职业经历与责任分析
```

应用可以提供案例、事实和证据，但不得重新定义概念。Robotaxi 应用继续区分系统模拟事实、工程完成状态和真实行业经营结果。

## 5. 知识对象与关系模型

### 5.1 概念对象

```text
Concept
- id：稳定且不随名称调整变化的标识
- name：正式名称
- definition：权威定义
- nature：概念性质
- plane：所属平面
- layer：阅读层级
- answers：概念回答的问题
- dependsOn：定义依赖
- parentContexts：所属上层结构
- relatedTo：相关概念
- distinguishesFrom：易混淆概念
- applications：应用引用
- source：上游来源
- sourceVersion：来源版本
- status：固定 / 发展中 / 待验证
- updatedAt：同步时间
```

### 5.2 关系对象

架构线和概念链接必须声明关系语义：

```text
Relation
- id
- source
- target
- type
- label
- direction
- context
- sourceReference
```

第一版允许的关系类型：

- 企业现实关系：构成、参与、进行、产生、影响；
- 设计与实现关系：驱动、指导、提出需求、形成、进入；
- 运行反馈关系：记录、计算、衡量、支持、调整；
- 知识关系：依赖、限定表达、属于、相关、区别于；
- 应用关系：应用于、由事实支持。

不同关系不能只使用无文字箭头统一表达。关系标签是认知内容的一部分，不是装饰。

### 5.3 单一权威定义

同一概念的权威定义只存储一次：

```text
概念定义
   ├─ 被总览引用
   ├─ 被局部结构引用
   ├─ 被概念页引用
   └─ 被应用页引用
```

页面只能压缩显示、引用或展开，不得复制后独立修改。

## 6. 核心用户路径

### 6.1 从整体进入概念

```text
作品入口
→ 企业经营体系总览
→ 经营与架构设计
→ 企业业务架构
→ 概念详情
```

目标：读者三次主要选择内到达“企业业务架构”权威定义。

### 6.2 从概念追溯到底层

```text
企业业务架构
→ 业务对象与事件
→ 业务对象
→ 对象
```

目标：读者能够知道“业务对象”不是新增底层概念，而是“对象”在企业业务架构中的限定表达。

### 6.3 从概念进入应用

```text
企业能力
→ Robotaxi 应用
→ 供给规划能力
→ 对应业务对象、规则、流程和指标
→ 可验证项目证据
```

目标：抽象概念和具体作品互相连接，但不混淆定义与证据。

### 6.4 返回与比较

用户下钻后必须能够：

- 返回上一级结构；
- 返回原始总览位置；
- 查看已经经过的认知路径；
- 在两个易混淆概念之间切换比较；
- 通过浏览器前进、后退恢复状态。

## 7. 交互设计合同

### 7.1 快速预览

桌面悬停和键盘聚焦显示：

- 正式名称；
- 一句话定义；
- 概念性质；
- “查看详情”行动。

快速预览不承载二次悬停、不形成嵌套浮层、不替代完整定义。

### 7.2 稳定详情

点击概念后：

- 桌面优先使用与架构图并存的详情区；
- 当前节点、直接上游、直接下游和关系线获得明确状态；
- 详情中的概念链接替换当前详情并更新认知路径；
- 点击空白或明确关闭操作可以返回完整总览；
- URL 或可恢复状态应表达当前选中概念。

详情区的最终位置、宽度和页面构图由结构与视觉 task 用真实构图验证，产品方案只固定其信息责任和状态行为。

### 7.3 深度阅读

当概念包含完整定义、辨析、关系和应用时，允许进入独立概念页。独立页必须保留：

- 所属平面；
- 上层结构；
- 定义依赖；
- 相关概念；
- 应用入口；
- 返回探索现场。

### 7.4 手机交互

手机没有悬停，采用：

- 点击节点后打开底部抽屉或进入独立详情；
- 总览按语义重排为纵向关系，不缩小桌面整图；
- 返回操作保持原来的展开位置；
- 核心概念和关系标签保持可读；
- 不以横向拖动画布作为默认学习路径。

底部抽屉和独立详情之间的选择由结构与视觉 task 通过 390px 和 320px 构图验证。

### 7.5 可访问性

- 所有悬停信息必须也能通过键盘聚焦和点击获得；
- 当前节点不能只依赖颜色表达；
- 节点具有明确的可交互语义和焦点样式；
- Escape、焦点恢复和浏览器历史行为必须可预测；
- 动效只帮助理解状态变化，不承担必要信息。

## 8. 信息架构与页面范围

### 8.1 入口关系

```text
作品
└─ 企业经营体系认知框架
   ├─ 总览
   ├─ 局部结构
   ├─ 概念详情
   ├─ 底层概念
   ├─ 应用
   └─ 框架说明
```

这些是产品内部阅读结构，不要求全部成为导航栏或独立路由。

### 8.2 第一版页面和状态

必须覆盖：

- 作品入口摘要；
- 认知框架总览默认状态；
- 一个平面聚焦状态；
- 一个上层概念详情状态；
- 一条追溯到底层概念的路径；
- 一个 Robotaxi 应用示例；
- 桌面快速预览和详情状态；
- 手机总览和详情状态；
- 无 JavaScript 或交互失败时仍可阅读的基本内容顺序。

### 8.3 不做

- 新增一级“认知框架”导航；
- 无限自由画布；
- 自动知识图谱布局编辑器；
- 多层嵌套悬停；
- 用户账号、收藏和学习进度；
- AI 问答或 Agent；
- 在线修改上游权威定义的后台；
- 一次性软件化 v5.1 全部职业章节；
- 在产品方案未冻结前进入正式工程实现。

## 10. 结构与视觉复核任务

结构与视觉 task 不从零重做产品方案，而是用真实页面构图回答以下问题。

### 10.1 总览构图

- 四个平面能否一眼区分，又仍然属于同一企业经营体系；
- 是否存在不必要的节点、线条或重复说明；
- 关系标签在 1440、768 和 390px 是否仍可读；
- 总览是否先建立整体，而不是先暴露术语密度；
- 当前品牌的暖色编辑感与业务架构精度是否同时成立。

### 10.2 详情构图

- 架构图与概念详情并存时，哪一部分是主任务；
- 详情区是否遮挡关键上下文；
- 定义、性质、依赖、辨析和应用如何形成清楚层级；
- 用户切换概念时是否能察觉当前位置和关系变化；
- 侧栏、底部面板或页面内展开哪种结构更稳定。

### 10.3 深度与路径

- 面包屑是否足以表达认知依赖，还是需要独立路径轨迹；
- 连续下钻四至五层后是否仍能返回；
- 相关概念和定义依赖是否在视觉上被误认为同一种关系；
- 如何支持概念比较而不增加多窗口复杂度。

### 10.4 响应式

- 桌面关系图如何转化为手机纵向结构；
- 557px 紧凑页头和 520px 以下手机菜单是否保持现有合同；
- 320px 是否仍能阅读节点、关系和定义；
- 手机详情采用抽屉还是独立页更符合阅读深度；
- 是否存在必须依赖横向拖动才能理解的关系。

### 10.5 输出

结构与视觉 task 应交付：

- 桌面总览；
- 桌面概念详情；
- 手机总览；
- 手机概念详情；
- 一条完整下钻路径；
- 关键交互状态；
- 对产品方案的冲突、删减和优化建议；
- 仍未证实的构图假设。

结构与视觉 task 在完成上述验证并确定方案后，应直接把定稿结果和工程合同移交 Engineering，不需要常态返回产品方案 task。

## 11. 结构与视觉定稿及例外返回条件

结构与视觉 task 在产品边界内自行完成方案比较、构图优化和定稿，并补齐 Engineering 所需的页面状态、组件责任和响应式行为。

以下决策不需要返回产品方案 task：

- 侧栏、下方面板或页面内展开的选择；
- 桌面和手机的具体构图；
- 视觉层级、空间、字体、线条和交互反馈；
- 首版节点在不破坏主路径前提下的视觉取舍；
- 组件拆分和响应式投影方式。

只有出现以下根本冲突时才返回产品方案 task：

- 需要修改权威概念名称、定义或概念性质；
- 需要改变一个知识模型、五种阅读视图的产品结构；
- 需要扩大或缩小首版产品范围，而不只是构图取舍；
- 核心下钻、追溯、返回或应用路径在真实构图中无法成立；
- 产品合同存在明显不可实现或投入产出失衡。

没有触发以上条件时，结构与视觉定稿即为 Engineering 的直接输入。

## 12. Engineering 移交合同

最终移交不能只有效果图。至少包括：

- 上游来源和同步版本；
- 首版概念清单；
- 概念和关系数据结构；
- 页面和路由范围；
- 总览、聚焦、预览、详情、下钻、返回和应用状态；
- 桌面与手机投影规则；
- 结构与视觉定稿；
- 内容降级顺序；
- 键盘和可访问性要求；
- 自动测试落点；
- 真实浏览器验收视口；
- 明确不做范围。

Engineering 不得：

- 在组件中复制另一份概念定义；
- 根据页面方便新增无来源概念；
- 用无文字连线替代关系语义；
- 用多层 tooltip 模拟完整下钻；
- 将桌面关系图直接等比缩小到手机；
- 把尚未进入首版的高级交互作为实现前提。

## 13. 验收标准

### 13.1 认知任务

- 新读者能在一分钟内说清四个平面的基本区别；
- 从总览到“企业业务架构”不超过三次主要选择；
- 用户能从“业务对象”追溯到基础性质“对象”；
- 用户能区分定义依赖、结构归属、相关概念和应用关系；
- 下钻五层后仍知道当前位置并能返回；
- Robotaxi 应用不改变概念定义，也不扩大事实边界。

### 13.2 内容与模型

- 每个概念只有一份权威定义；
- 概念和关系均有稳定标识；
- 所有架构连线具有明确关系语义；
- 上游版本和同步时间可以追溯；
- 上游变化时可以识别受影响概念和视图。

### 13.3 交互与视觉

- 悬停信息也可以通过聚焦和点击获得；
- 桌面与手机都能完成总览、下钻、返回和应用路径；
- 当前节点、路径和关系不只依赖颜色；
- 架构图不因节点过多失去主关系；
- 1440、1024、768、557、520、390、320px 均完成真实页面验证；
- 视觉继续遵守 xingbuild 暖色编辑型品牌和现有响应式颜色合同。

### 13.4 工程闭环

- 内容、组件、路由、交互状态和测试使用同一模型；
- `npm run release:check` 通过；
- 本地真实运行验证通过；
- 实现完成、本地验证、提交、部署和公网验收分别报告。

## 14. 快速迭代方法

本能力采用短闭环，但每轮只验证一个关键不确定性：

```text
产品方案 v0.7.0 草案
        ↓
结构与视觉验证并定稿
        ↓
Engineering 最小实现
        ↓
真实页面任务验证
        ↓
下一轮局部修订
```

推荐的第一轮验证对象是：

> 企业经营体系总览 → 数字化实现 → 企业业务架构 → 业务对象 → 对象 → Robotaxi 应用。

这条路径同时覆盖宏观总览、局部关系、概念详情、底层追溯和场景应用，能够以最小内容量验证产品的完整逻辑。

快速迭代不意味着产品、视觉和工程同时改变未固定的底层规则。每轮必须明确：

- 本轮验证什么；
- 哪些概念和关系已经固定；
- 哪些构图仍是假设；
- 哪些结果来自真实页面；
- 哪些修改需要回到产品或上游框架。

### 14.1 高质量与使用量约束

协作默认采用一次主闭环：

```text
一次产品草案
    ↓
一次结构与视觉联合定稿
    ↓
一次 Engineering 最小实现
    ↓
一次真实页面联合验收
```

为减少重复分析和使用量：

- 所有 task 读取并更新同一份产品方案，不分别重写完整背景；
- 结构与视觉合并为一次联合定稿，不拆成两个重复分析 task；
- 不同时生成多套完整产品方案；只对尚未确定的构图问题比较有限选项；
- 结构与视觉确定后直接移交 Engineering，不进行常态 task 轮询；
- 产品方案 task 只在概念、范围、核心路径或投入产出发生根本冲突时重新介入；
- Engineering 不参与前期概念发散；
- 首次实现只覆盖一条完整主路径，不一次性实现全文全部概念；
- 验证优先使用现有测试、固定视口和一组可复用截图，不进行无目的全量复查；
- 已有证据足以回答问题时停止，不为了形式完整增加 task、文档或工具调用。

只有出现以下情况才增加一轮：

- 真实构图证明核心信息结构无法成立；
- 手机和桌面无法由同一知识模型稳定投影；
- 权威概念与页面需要的关系发生冲突；
- 核心任务路径未达到验收标准；
- Engineering 发现产品合同存在无法实现或代价明显失衡的问题。

局部间距、字体和微交互问题进入同一轮快速修订，不重新启动完整产品设计流程。
