# v0.8.0 架构结构优先审查与视觉重设计指令

当前《v0.8.0 单页交互式企业认知架构视觉提案》的品牌方向基本正确，但四张图的结构表达未通过。

问题不是颜色、字体或间距，而是：

> 当前效果图主要把概念排成卡片、网格和纵向列表，没有稳定表达核心对象、结构层级、关系方向、约束、支撑、结果和反馈，因此还不是结构性的架构图。

当前效果图不能移交 Engineering，也不应继续通过局部视觉润色修补。

## 2. 当前方案未通过的具体原因

### 2.1 架构一：反馈闭环没有形成系统结构

当前方案将七个节点拆成上下两排卡片，反馈关系通过底部一句文字补充。

结果：

- 企业经营体系、企业现实和四个平面的关系不清楚；
- “经营与架构设计”和“数字化实现”被误读为顺序相邻步骤；
- 企业运作、事实结果和反馈之间没有形成清晰闭环；
- 核心对象与支撑/反馈节点使用相同形状和权重；
- 用户需要读文字才能重建关系。

### 2.2 架构二：九宫格不是企业业务架构

当前方案只有顶部三项表达线性关系，下面六项被排成网格。

结果：

- 企业职能与组织责任如何承接能力不清楚；
- 业务流程如何改变对象状态不清楚；
- 业务规则约束什么不清楚；
- 事实、指标与经营目标差距如何形成反馈不清楚；
- 读者看到的是分类清单，不是价值形成和执行结构。

### 2.3 架构三：转化链缺少层级与汇合

当前方案虽然包含业务、产品、数据、技术、工程和系统，但需要明确：

- 哪一层提出需求；
- 哪两条设计轨道并行；
- 在哪里汇合；
- 什么是实现活动；
- 最终形成什么现实系统；
- 系统如何进入企业现实并产生事实反馈。

如果只使用同级矩形和顺序箭头，仍会被理解为项目步骤。

### 2.4 架构四：五组分类仍不是底层语法关系

将十个概念分入五列只能表达分类，不能表达：

- 主体如何围绕对象参与活动；
- 关系和状态如何构成现实结构；
- 事件如何改变状态和关系；
- 规则约束活动和变化；
- 事实如何记录；
- 指标如何衡量状态、过程和结果。

### 2.5 手机端退化为线性列表

手机使用“节点—箭头—节点”纵向排列，虽然可读，但丢失：

- 并行关系；
- 包含关系；
- 支撑关系；
- 约束关系；
- 反馈回路；
- 多视角观察同一现实的结构。

手机可以改变方向，不能改变关系性质。

## 3. 架构图必须先遵守的结构语法

结构视觉 task 在画图前必须先为每个节点确定角色：

| 结构角色 | 视觉责任 |
| --- | --- |
| 核心研究对象 | 全图主锚点，不与普通节点同权重 |
| 外部条件或触发 | 位于系统边界外或起点位置 |
| 结构容器 | 包含相关现实对象或设计层 |
| 设计层 | 表达选择、设计与指导 |
| 支撑层 | 表达资源、数字化或能力支撑 |
| 执行主链 | 表达活动实际如何发生 |
| 约束 | 从侧面作用于活动、状态或关系 |
| 事实与结果 | 接收执行输出 |
| 衡量与反馈 | 从结果返回目标、设计或运作 |

连接线必须先确定关系性质：

- 触发；
- 构成；
- 设计；
- 指导；
- 提出需求；
- 支撑；
- 执行；
- 约束；
- 改变；
- 产生；
- 记录；
- 衡量；
- 反馈；
- 调整。

不同关系不能只靠同一种箭头表达。优先通过位置、方向、线型和短标签共同表达；颜色只做当前互动状态，不作为唯一语义。

## 4. 四张图的结构骨架

以下固定“关系骨架”，结构视觉 task 可以优化构图，但不能退化为卡片列表。

### 4.1 架构一：企业经营体系整体结构

必须表达三层关系：

```text
外部环境、利益相关者与需求
              │ 影响与约束
              ↓
┌────────────────────────────────────────┐
│            企业经营体系                │
│                                        │
│  经营与架构设计 ──建设和调整──→ 企业现实 │
│          │ 提出数字化需求        │       │
│          ↓                       │ 进行  │
│      数字化实现 ──形成并进入─────┘       │
│                                  ↓      │
│                              企业运作    │
└──────────────────────────────────│──────┘
                                   ↓ 产生
                            事实与经营结果
                                   │ 支持
                                   ↓
                             经营分析与决策
                                   │ 调整
                                   └────────→ 经营与架构设计 / 企业现实
```

关键要求：

- “企业经营体系”是结构容器或全图核心，不是普通卡片；
- “企业现实”是被设计、被建设并实际运作的现实对象；
- “经营与架构设计”与“数字化实现”是不同性质的层；
- 反馈必须视觉闭合，不能只写一句说明；
- 第一眼先看到系统关系，再看到具体文字。

### 4.2 架构二：企业业务架构

使用一条价值形成与执行主脊柱，其他视角附着其上：

```text
利益相关者需求 / 业务事件
          │ 触发
          ↓
       价值流
          │ 需要
          ↓
企业能力与资源 ←── 企业职能归类 / 组织承担
          │ 通过
          ↓
       业务流程 ←── 业务规则约束
          │ 改变
          ↓
  业务对象的状态与关系
          │ 产生
          ↓
      事实与结果
          │ 由指标衡量
          ↓
价值流结果与经营目标差距
          │ 反馈
          └────────→ 能力、流程、规则与资源调整
```

关键要求：

- 主脊柱表达价值如何被组织和执行；
- 企业职能、组织责任是责任承接，不是主流程步骤；
- 业务规则从侧面约束；
- 指标属于衡量，不属于执行步骤；
- 反馈返回设计对象；
- 九个视角必须在同一企业现实中形成关系。

### 4.3 架构三：数字化实现

使用分层与双轨汇合结构：

```text
企业业务架构
      │ 提出数字化需求
      ↓
┌────────────设计层────────────┐
│ B 端产品架构  ↔  数据架构    │
└──────────────│───────────────┘
               │ 共同驱动
               ↓
          技术架构
               │ 通过
               ↓
            工程实现
               │ 形成
               ↓
       企业数字化系统
               │ 进入、支持或执行
               ↓
      企业现实与企业运作
               │ 产生并记录
               ↓
        事实与经营结果
```

关键要求：

- 产品架构与数据架构必须视觉并行且相互关联；
- 技术架构与工程实现不能混成同级设计名词；
- 数字化系统是实现结果，不是架构同义词；
- 最后必须进入企业现实，而不是停在“系统上线”；
- 可以表达事实反馈，但不与架构一重复绘制完整经营闭环。

### 4.4 架构四：底层概念语法

使用主因果链和交叉约束/衡量关系：

```text
主体 ──围绕── 对象
  │             │
  └──参与──→ 活动与过程 ←──规则约束
                    │ 作用于
                    ↓
                  对象

事件 ──改变──→ 状态 / 关系
  │                 ↑
  └──受到规则约束───┘

活动与事件 ──形成──→ 结果

状态 / 活动 / 事件 ──由事实记录或验证──→ 事实
事实 ──提供计算依据──→ 指标
指标 ──衡量──→ 状态 / 过程 / 结果
```

关键要求：

- 五个阅读分组可以作为辅助标识，不能代替关系图；
- 规则应表现为横向约束；
- 事实、指标和结果不能被画成简单先后步骤；
- 允许用两条关联主链，但必须让交叉关系可追踪。

## 5. 顶级网页机制的定向学习

只学习与当前失败直接相关的机制。

### 5.1 Kumu Systems Mapping

参考：

- https://www.kumu.io/markets/system-mapping
- https://docs.kumu.io/disciplines/system-mapping

学习：

- 先建立元素、连接和回路，再做装饰；
- 点击元素、连接或回路后显示稳定叙述；
- hover 只突出直接相关元素并弱化其他内容；
- 复杂系统可以通过焦点逐步揭示，但完整系统结构仍然存在。

不复制无限画布、彩色气泡和工具型控制。

### 5.2 Nicky Case Explorable Explanations / LOOPY

参考：

- https://blog.ncase.me/how-i-make-an-explorable-explanation/
- https://ncase.me/loopy/

学习：

- 互动不是附加效果，而是帮助用户理解因果和反馈；
- 用户操作后应看到关系发生了什么，而不只是阅读另一段定义；
- 先让用户直观看到系统，再提供解释。

不复制游戏化、手绘或彩色动画风格。

### 5.3 IBM Technical Diagrams

参考：

- https://www.ibm.com/design/language/infographics/technical-diagrams/design/

学习：

- 网格、节点层级、嵌套容器和正交连接；
- 节点尺寸和连接点一致；
- 关系使用标签、线型和方向表达；
- 颜色不能单独承担关系语义。

不复制 IBM 品牌。

### 5.4 Vexlio / SchemaFlow / Nodefall

参考：

- https://vexlio.com/templates/interactive-architecture-diagram/
- https://www.schemaflow.dev/
- https://www.nodefall.dev/

学习：

- 整体结构默认存在，细节按点击提供；
- 节点和连接都可以承载解释；
- 高亮当前路径、弱化非当前路径；
- 动效可以用于追踪流动顺序，但不能掩盖静态结构。

不引入编辑器、无限画布、云服务图标和演示型炫技。

## 6. xingbuild 的交互表达

### 6.1 默认

- 完整架构可读；
- 核心对象、容器、执行链、约束和结果有结构差异；
- 不依靠选中状态才能理解图。

### 6.2 hover / focus

- 当前节点轻微上浮；
- 直接相邻节点和连接线增强；
- 非相关内容降低到约 `45–60%` 的视觉权重，但文字仍可辨认；
- 不显示长 tooltip；
- focus 与 hover 等价。

### 6.3 click / selected

- 当前节点保持选中；
- 显示所有直接入边和出边；
- 右侧解释优先说明“它在当前结构中承担什么作用”和“与谁发生什么关系”；
- 不能只重复权威定义；
- 如果选择反馈节点，应高亮完整反馈路径，而不只高亮一条边。

### 6.4 手机

手机不是把所有节点拉成单链。

允许：

- 将横向主脊柱改为纵向；
- 将侧面约束放到主链节点下方或嵌套区域；
- 将反馈回路表现为明确的返回轨道；
- 使用紧凑分组边界维持并行和包含关系。

禁止：

- 把并行关系变成先后关系；
- 把约束变成流程步骤；
- 把反馈删除为一句文字；
- 只保留节点名称和向下箭头。

## 7. 高质量、低使用量协作路径

只执行一次结构校正和一次高保真效果图：

```text
本审查固定四张图结构骨架
        ↓
结构视觉 task 先形成四张低保真结构图
        ↓
产品 task 一次性检查对象、层级和关系
        ↓
结构视觉 task 形成一个高保真推荐方向
        ↓
用户确认效果图
```

限制：

- 不生成三套完整视觉方向；
- 不重新研究与当前问题无关的网站；
- 不重复讨论已固定的单页、四图和左右解释结构；
- 低保真阶段只看结构，不优化字体和装饰；
- 高保真阶段只对已通过的结构应用 xingbuild 视觉；
- 用户确认前不进入 Engineering。

## 8. 结构视觉 task 下一次交付

第一次返回产品 task 的内容仅限：

1. 四张低保真结构图；
2. 每张图的核心对象、主链、侧向关系和反馈说明；
3. 桌面与手机如何保持同一关系；
4. 选择的两个到四个外部学习对象，以及具体继承的机制；
5. 一项明确推荐，不提供多套完整方向。

产品 task 只检查：

- 对象性质是否混淆；
- 层级是否正确；
- 关系是否缺失或错误；
- 手机是否改变关系性质。

结构通过后，再制作高保真效果图并交用户确认。
