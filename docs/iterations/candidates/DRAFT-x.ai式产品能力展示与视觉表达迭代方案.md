## 1. 本方案要解决的问题

### 1.1 用户含义

本轮不是把 xingbuild 改成 x.ai 的黑色网站，也不是引入浅色/深色/系统主题。

明确保留：

- 当前 xingbuild 暖色编辑型视觉；
- 当前浅色主题；
- 当前一级信息架构 `B端产品 / 经营观察 / 关于我`；
- 当前 Observation、Article、Practice、About 内容对象；
- 当前内容发布与产品版本分离；
- 当前文章和页面的阅读优先结构。

只学习 x.ai/cli 的产品表达机制：

```text
能力说明
    ↓
同一空间中的真实能力演示
    ↓
用户理解它如何工作
    ↓
继续阅读、操作或进入独立系统
```

### 1.2 当前结构性问题

当前 xingbuild 已经有 `ShowcaseLayout`、`SystemStage`、`RichDocument` 和 source-driven figure，但这些能力之间还没有统一的“产品能力展示控件”合同：

- 页面说明、媒体、架构图和受控系统空间的责任容易混在一起；
- 视觉区域常被当作图片槽，而不是可验证的产品状态空间；
- 新增一个演示状态可能需要页面专用组件或 CSS；
- 内容对象还不能只通过声明调用统一展示能力；
- hover、focus、click、tap、loading、error、fallback 和状态切换缺少统一验收。

因此本轮要建立的是“展示能力层”，不是重新设计网站页面。

### 2.4 本次对 x.ai/cli 的只读学习结论

本次同时观察桌面与 `390 × 844` 移动视口，学习的是产品展示机制，不是主题换肤：

- **全局顶部行动带**：页面最上方是一条横向、固定高度的全局区域；品牌在一侧，主要行动按钮和菜单在另一侧。移动端折叠为品牌、行动按钮、菜单按钮，滚动后仍保持可达，不把行动按钮藏进正文。
- **标题上方的上下文行动**：首屏标题之前可有一条横向的公告/上下文入口（类似 x.ai 的 announcement pill），它是可点击的产品状态入口，不是装饰性标签。它必须有明确目的、目标和可关闭/不可用时的降级。
- **能力段落的节奏**：大标题、解释、操作入口、能力演示、结果或下一步按稳定顺序进入同一页面流；演示不是脱离文档的浮层，也不是静态截图槽。
- **移动端重排**：标题自然换行，说明和演示保持可读宽度；演示卡片、列表和图形继续占据文档流，不依赖 hover 才能理解。按钮保留足够触控面积，不能以桌面比例压缩为不可读缩略图。
- **滚动与反馈**：页面采用连续的自然纵向滚动，固定顶部栏在滚动后仍保留行动入口；交互反馈主要由颜色、边界、焦点和轻量过渡表达，不把滚动本身当成必需的复杂动画。当前没有把“滚动触发动画”当成已确认能力，若未来采用必须另行验收。
- **字体与密度**：能力标题、说明、操作文字、状态/metadata 和演示内部文字有稳定角色层级；移动端调整字号和行长而不改变角色关系。xingbuild 只移植层级、留白、节奏和交互反馈，字号仍由现有视觉 token 决定。

这意味着 xingbuild 需要的是可复用的 `PageFrame / TopBand / CapabilityStage / RichDocument / ClosingSection` 结构合同，而不是为某一个页面复制 x.ai 的 JSX 或 CSS。

## 3. 目标读者与阅读问题

| 读者 | 当前阅读问题 | 展示能力要证明什么 |
| --- | --- | --- |
| 首次访问者 | 这个作品/系统到底能做什么 | 看到一个明确、可理解的能力状态 |
| 产品/业务专业读者 | 业务对象如何进入系统操作 | 看到对象、动作、状态和结果的关系 |
| 工程读者 | 页面是否只是截图或营销描述 | 看到受控、可验证、可降级的运行投影 |
| 本人及内容 task | 后续增加模块是否需要改页面 | 只编辑内容声明即可复用同一展示控件 |

每个展示 section 只回答一个问题，不同时表达系统架构、经营闭环、用户流程和工程细节。

## 4. 推荐产品能力：统一 Capability Stage

候选名称：`CapabilityStage（能力展示空间）`。正式命名待 Engineering 评估现有 `SystemStage` 是否演进或由新 host 包装，不在本草案中提前锁死代码名。

### 4.1 结构

```text
Content Object / Page Section
        ↓
Capability Presentation 声明
        ↓
CapabilityStage 统一展示控件
        ├─ 静态媒体
        ├─ 文档图形
        ├─ LikeC4 架构视图
        ├─ Mermaid 流程/状态/生命周期
        └─ 受控 Robotaxi 系统空间
```

页面只提供展示位置和内容对象，控件负责空间、状态、交互、错误、降级与响应式。

### 4.2 最小内容声明

```text
id
kind: media | architecture | flow | state | lifecycle | interactive-system
sourcePath / mediaId / route
renderer?
initialState?
title?
summary?
alt
caption
action?
fallback?
provenance?
```

内容声明不得包含：

- 节点坐标；
- SVG path；
- 页面专用宽高；
- 视口专用文案；
- 只为修复某个页面而存在的 CSS 类；
- 未经上游批准的业务事实或系统状态。

### 4.3 统一状态模型

每个能力展示至少能表达：

```text
idle       初始状态
active     用户已进入或开始操作
selected   当前对象/节点/步骤
result     已产生可阅读结果
error      运行失败但有明确说明
fallback   使用批准的静态或文本降级
```

状态切换必须：

- 不重排页面整体几何；
- 不让关系线、节点或主要文字突然消失；
- 在手机 tap、桌面 click、键盘 Enter/Space 下保持语义一致；
- 能返回初始状态；
- 失败时不伪装成成功。

### 4.4 关键判定：空间与内容共同自适应

响应式不是每次新增内容都重新研发，而是 `CapabilityStage / VisualizationHost` 的基础产品能力。它必须同时适配“放置空间”和“空间中的表达内容”：

```text
内容语义声明
  → 选择 renderer 与响应式投影
  → 适配可用宽度、可读高度和交互方式
  → 保持对象关系、状态和降级
```

因此：

- 内容 task 只提供源文件、表达类型、语义元数据和批准的 fallback；不写桌面/手机 CSS、坐标、路径或断点分支。
- 展示控件负责单栏/双栏、图文顺序、可用尺寸、字体层级、SVG/DOM 缩放、触控/键盘和无横向溢出。
- renderer 负责内容本身的响应式投影：例如图片选择合适资源，视频保持可控比例，架构图选择 desktop/mobile 生成结果，互动系统切换到适合触控的布局。
- 自适应不能只靠外层 `width: 100%`；固定桌面图、固定节点坐标或把复杂系统压成缩略图都不算完成。
- 同一内容对象在桌面、紧凑宽度和手机可以有不同投影，但语义、状态、标题、说明和返回路径必须一致。

这就是“内容可更改、展示能力不反复开发”的产品边界：

| 情况 | 是否需要研发 |
| --- | --- |
| 新增同一种图片、视频、Mermaid 图或既有互动模块 | 否，内容发布只更新声明和源文件 |
| 同一 renderer 增加一个章节、十张图或一个新状态 | 否，走内容检查和发布 |
| 新增表达类型、交互模型、布局策略或 renderer adapter | 是，启动一次产品版本，能力完成后再由内容复用 |

## 5. 与现有网站结构的兼容

### 5.1 B端产品页

沿用当前结构：

```text
左：产品模块说明
右：CapabilityStage
下：产品长文和经营闭环解释
旁：Observation rail（有有效 Brief 时）
```

Robotaxi 模块可以从批准媒体逐步升级为受控系统演示，但：

- 不自动绕过 Robotaxi 登录；
- 不伪造已登录状态；
- 不新增未经批准的访问记录；
- 不把模拟作品表达为真实城市运营；
- 独立系统访问仍保留明确的外部入口。

### 5.2 企业经营体系长文

文章仍然是 `EvergreenArticlePublication + RichDocument`。

未来可以在文章中声明：

- 一张局部 Mermaid 流程图；
- 一个 LikeC4 架构视图入口；
- 一个章节级的受控视觉能力空间。

文章正文、目录、图形和 caption 仍由内容对象控制；文章页面不为某一张图写专用 JSX。

### 5.3 Observation Brief

不改变短文结构、事实审核、来源合同或发布流程。

Brief 只可以在未来引用一个已批准的能力展示对象；没有必要时不增加图形或互动，避免把短文变成产品说明页。

### 5.4 About

继续使用 `RichDocument`。只有当某个能力确实帮助读者理解作者的工作方法时，才允许加入能力展示 block；不把 About 改成工具产品页。

### 5.5 页面组合承接

页面定义、导航关系、`TopBand`、可选 `left/right`、`RichDocument`、`ClosingSection` 及移动端顺序，统一以唯一现行总案的“页面产品架构与组合合同”和“PageComposition 共享区域”为准。本文不重复维护这些结构，避免候选方案与已确认产品基线漂移。

本文只继续定义能力展示层如何嵌入这些组合：`CapabilityStage / VisualizationHost` 必须能够作为 `right`、`body` 或文章 block 的内容对象使用；内容声明提供表达类型和来源，控件负责空间、自适应、互动状态与降级。

## 6. 视觉方案：学习机制，保留 xingbuild 身份

### 6.1 采用的视觉机制

- 让展示空间成为 section 的视觉主角；
- 说明、状态、操作和结果有清晰层级；
- 使用精确线条、开放留白和稳定的空间比例；
- 演示区域有真实边界，但不使用任意卡片堆叠；
- 状态变化只改变必要的颜色、强调、内容和控件，不移动整体布局；
- 信息密度由对象和状态决定，不用大面积空白掩盖没有内容的区域；
- 可操作区域提供克制 hover、focus-visible 和 tap 反馈。

### 6.2 保留的 xingbuild 视觉规则

- 暖白 `--color-canvas`、墨色正文、赭色强调；
- Noto Serif SC 负责编辑型标题和正文；
- Noto Sans SC 负责导航、状态、metadata 和操作；
- 当前浅色主题保持不变；
- 不增加 dark、light、system 三态主题；
- 不把 x.ai 的黑白高对比度作为全站视觉方向；
- 不改变 Header、Footer、一级导航和内容对象结构。

### 6.3 CapabilityStage 的视觉合同

桌面：

```text
说明列 → 关系间距 → 能力展示空间
```

移动：

```text
对象标题/摘要 → 能力展示空间 → 说明/结果
```

合同：

- 展示空间拥有统一的最大宽度、最小可读高度和安全内边距；
- 不与外部页面组件边缘共线重合；
- 空状态、错误状态和 fallback 使用同一视觉层级；
- hover 不改变尺寸；
- 选中不导致节点、线或文本重排；
- 控件不会遮挡主要内容；
- 不产生嵌套纵向滚动；
- 文字和图形均有静态/文本降级。

### 6.4 从 x.ai 学到的互动与字体合同

- 顶部 `TopBand` 的行动按钮与菜单按钮是可聚焦、可点击的真实控件；桌面支持 hover、focus-visible、click，移动端使用 tap，不能把 hover 当作唯一信息来源。
- 标题上方的 `action?` 只表达一个清楚的上下文动作（例如进入演示、打开文档或查看下一层）；不在同一横向带堆叠多个 CTA。没有目标时隐藏该 action，而不是显示无效按钮。
- 能力区的状态切换只更新选中、说明、结果或错误提示；不改变页面列数、标题位置、图形坐标或上下文滚动位置。动画必须尊重 `prefers-reduced-motion`，并在不支持动画时保持语义完整。
- 字体角色固定为 `page title → section title → explanation → operation → state/metadata → source/caption`；移动端允许缩小字号和增加换行，但不逆转层级、不用超大标题吞掉能力演示。
- 点击、键盘和触控共享同一状态机；按键、点击或 tap 后必须有可见反馈，并能回到初始状态。焦点恢复、目录跳转和返回导航遵循全站既有合同。
- 连续滚动必须保持稳定的顶部栏、无横向溢出、无嵌套纵向滚动；滚动期间不因懒加载、状态提示或演示尺寸变化造成页面跳动。
- 图形、媒体和受控系统都必须有 `alt/caption` 或文本结果；加载失败显示真实 `error/fallback`，不能用空白框假装能力已运行。

## 7. 迭代计划候选

### 阶段 0：当前设计确认（本草案）

范围：

- 确认“学习能力展示机制，不复制主题和页面”的方向；
- 确认 `CapabilityStage` / `VisualizationHost` 的产品责任；
- 确认 B端产品、文章图形和 Observation 的边界；
- 确认验收合同和非目标。

不做：代码、current、VERSION、依赖、内容发布、Robotaxi 工程修改。

### 阶段 1：候选 `v0.22.0+`——统一能力展示控件

建议只做一个最小产品版本：

1. 在现有 `ShowcaseLayout` 和 `RichDocument` 之上建立统一 stage 合同；
2. 让一个 Robotaxi 模块和一个文章图形使用同一套声明式展示入口；
3. 统一 idle/active/selected/result/error/fallback 状态；
4. 统一桌面、紧凑宽度和手机的展示空间；
5. 让空间和内容共同自适应，内容声明不携带页面断点或几何；
6. 不改变主题、不重做 Header/Footer/IA、不修改 Observation Brief；
7. 不在本版本一次性实现所有 LikeC4 多视图和所有图形工具。

Engineering 只在本文确认并进入 `current.md` 后开始实现。

### 阶段 2：内容运营接管

当 stage 合同稳定后：

- 内容 task 只更新能力声明、图源、说明和 caption；
- 增加十张图、多个章节或新模块不再修改页面组件；
- 每篇文章和每个模块继续独立检查和发布；
- 产品版本/tag 保持不变。

### 阶段 3：按需增加 adapter

按真实内容需求逐个增加：

1. LikeC4 原生多视图架构；
2. Mermaid 流程、状态、生命周期和时序；
3. 其他开源 adapter。

每个 adapter 单独验证，不因为“工具存在”就自动进入网站运行时。

## 8. 产品验收合同

### 结构

- 内容对象只声明能力，不声明页面几何；
- 同一能力可以嵌入 B端产品、长文或其他允许的 section；
- 普通 Brief 不被改造成产品演示页；
- 页面不会因为增加内容对象而复制专用组件；
- `TopBand` 能选择左对齐或居中标题，标题说明和上下文 action 可独立存在或省略；
- `ContentComposition` 支持单栏、左右双栏和关闭任一侧，不为关闭区域保留空占位；
- `RichDocument` 和 `ClosingSection` 能按声明进入页面，不改变页面类型；
- `ClosingSection` 支持标题-only、标题+说明和省略三种状态。
- 同一内容对象在桌面、紧凑宽度和手机使用合适投影，不要求内容 task 为每个视口维护一套页面代码。

### 视觉

- xingbuild 暖色视觉保持一致；
- 展示空间是视觉主角但不侵占页面层级；
- 说明、状态、操作和结果可快速识别；
- 线条、矩形和文字不与无关组件边缘重合；
- 不能出现巨大的空白矩形、不可读缩放或孤立标签。

### 交互

- 桌面 hover/focus/click 和手机 tap 均有明确反馈；
- 键盘 Enter/Space 路径成立；
- 选中、返回、复位和错误恢复不改变页面整体布局；
- 不自动登录、不伪造状态、不生成未授权业务记录；
- 能力运行失败时有可读 fallback。

### 响应式

- 至少验证 1440、1024、768、557、390、320；
- `scrollWidth === clientWidth`；
- 无嵌套纵滚；
- stage 与说明的归属间距稳定；
- 不用桌面图形压缩成手机不可读缩略图；
- 移动端验证顶部行动带、标题自然换行、按钮触控面积、目录/长文流和能力空间顺序；
- 验证滚动前后顶部行动入口可达，且内容不因状态或媒体加载发生跳动；
- 用同一内容声明验证图片、视频、架构图和互动空间的“容器适配 + 内容投影适配”，而不是只验证外层宽度。

## 9. 当前未决事项

1. `SystemStage` 是直接演进为统一能力控件，还是由新的 `CapabilityStage` 包装；
2. `v0.22.0+` 首个 pilot 选择 Robotaxi 互动模块还是文章图形；
3. LikeC4 原生 runtime 是统一能力控件的首个 adapter，还是作为后续独立能力；
4. Robotaxi 受控互动空间是否需要独立 `/embed`；
5. x.ai 式演示是否需要独立的“状态说明/结果栏”，还是复用现有文章和模块说明；
6. `TopBand` 的默认对齐（左对齐或居中）以及上下文 action 的首个真实目标；
7. `ClosingSection` 是否先在首页试点，还是先由长文内容提供。

这些事项必须在产品确认后再进入 Engineering，不由 Engineering 在实现时自行决定。
