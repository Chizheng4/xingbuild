# 内容运营与发布问题清单

## 使用边界

本清单是候选采集、事实审核、单条发布和公网验收问题的唯一 tracked 入口；不展示给网站读者。task 不是问题数据库，跨 task 只传问题 ID、当前状态、证据路径、责任人和下一动作。

只有同时具备可验证证据和实际影响的问题才登记。想法、偏好、无证据猜测和已经由现有规则覆盖的正常状态不进入清单。发现者可以登记问题，但不得借登记自行修改产品、规则或工程实现。

## 统一状态与字段

状态只使用：

`待评估 → 已确认 → 待实施 → 实施中 → 待验收 → 已关闭`

无法继续时使用 `等待上游输入`；经评估不处理时使用 `不处理`，并记录理由。

每项至少包含：

- 唯一 ID、状态和发现日期；
- 事实证据、影响与风险；
- 当前临时控制；
- 责任域与责任 task；
- 是否需要产品版本；
- 已批准方案或下一动作；
- 完成后的 commit/tag（如适用）与验证结果。

## 处理规则

- 内容运营内部规则问题可以独立 tracked 文档提交修正，不改变产品版本或 tag，也不触发部署。
- 只有公开内容对象、信息架构、页面投影、视觉/响应式或发布能力合同需要改变时，才由产品与视觉 task 评估并转入 `docs/iterations/current.md`。
- Engineering 只实现已经批准并进入当前迭代的问题，不顺手修复清单中的其他项。
- 内容提交只能包含目标 Observation 与必要 approved media，不夹带问题清单或规则修正。
- 关闭问题时保留原问题、修复事实和验证结果；不删除记录，不把完整 task 历史复制进来。

### OPS-CONTENT-001：缺少可核验的月度采集覆盖台账

- 状态：已关闭
- 发现日期：2026-07-30
- 证据：当前已发布或隔离的 7 月事件覆盖 2026-07-04 至 2026-07-28；仓库没有按月记录采集窗口、已检索来源、去重结论与空白日期，因此不能证明“7 月已采集至今天”。
- 影响：内容负责人无法区分“没有高价值事件”与“尚未覆盖该日期”，补采依赖临时检索，容易造成遗漏或重复。
- 当前临时控制：日常发布仍按 slug 独立合同执行，不因覆盖记录缺失降低来源或审核门槛。
- 责任域：Ops 内部运营；不需要产品版本。
- 解决结果：`b823db1` 建立经营观察信息源与覆盖合同，`ca55e95` 增加来源注册表和共享覆盖检查点；定时与按需采集使用同一覆盖事实。
- 验证结果：2026 年 5 月回溯已按覆盖记录完成，能够区分已覆盖无合格事件、未覆盖和低增量不发布；治理记录未进入读者界面。

### OPS-CONTENT-002：来源覆盖合同与 EvidenceCandidate 写入路径不一致

- 状态：已关闭
- 发现日期：2026-07-30
- 证据：`docs/operations/经营观察信息源与覆盖合同.md` 第 42 行仍规定候选写入 `.content-workspace/imports/`；现行 `.content-workspace/ops/evidence-candidate-contract.md` 则明确 Ops 只能写入 `.content-workspace/ops/candidates/`，后者是当前有效候选边界。
- 影响：若 Ops 依照旧文档写入 imports，内容 task 可能误把非生产形态 EvidenceCandidate 交给 import/approve，破坏候选与 ObservationPublication 的对象边界。
- 当前临时控制：2026 年 5 月补采严格只接受 `.content-workspace/ops/candidates/`，未把 EvidenceCandidate 交给 import/approve。
- 责任域：Ops 与内容运营内部规则；不需要产品版本。
- 解决结果：来源覆盖合同已明确 `EvidenceCandidate` 只进入 `.content-workspace/ops/candidates/`；只有内容 task 人工形成的完整 `ObservationPublication` 才进入 `.content-workspace/imports/`。
- 验证结果：对象边界与 AGENTS 三段职责一致；规则修正未混入五条独立内容提交，也不改变产品版本、UI 或生产 bundle。
