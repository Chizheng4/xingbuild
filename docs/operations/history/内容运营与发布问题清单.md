# 内容运营与发布问题清单（历史归档）

> 本文件只保存历史事实和关闭证据，不是工作流入口。任何新问题或优化必须写入 `docs/iterations/candidates/<candidate-id>.md`，由产品与视觉 task 评审；日常运行证据只写被忽略的 `.content-workspace/ops/`。

## 使用边界

历史上本清单曾记录候选采集、事实审核、单条发布和公网验收问题；自统一候选入口生效后不再是 tracked 工作流入口。它不展示给网站读者，task 也不是问题数据库；跨 task 只传问题 ID、当前状态、证据路径、责任人和下一动作。

只有同时具备可验证证据和实际影响的问题才登记。想法、偏好、无证据猜测和已经由现有规则覆盖的正常状态不进入清单。发现者可以登记问题，但不得借登记自行修改产品、规则或工程实现。

本历史文件覆盖过内容运营全链路：来源采集与覆盖、EvidenceCandidate、事实审核、Brief/Article/Practice 字段适配、slug 级命令、独立内容提交、push、EdgeOne、公网验收、失败重试和 workspace 清理。新的产品 DRAFT、视觉意见、工具缺陷和页面能力一律转入 `docs/iterations/candidates/`，不得在此新增活动条目。

## 统一状态与字段

状态只使用：

`待评估 → 已确认 → 待实施 → 实施中 → 待验收 → 已关闭`

无法继续时使用 `等待上游输入`；它表示责任 task 已记录所缺输入、回传对象和恢复条件并结束当前回合，不表示持续调用等待或轮询工具。经评估不处理时使用 `不处理`，并记录理由。

每项至少包含：

- 唯一 ID、状态和发现日期；
- 事实证据、影响与风险；
- 当前临时控制；
- 责任域与责任 task；
- 是否需要产品版本；
- 产品候选 ID（只有影响产品能力时填写，完整优化方案只放在 `docs/iterations/candidates/`）；
- 已批准方案或下一动作；
- 完成后的 commit/tag（如适用）与验证结果。

## 处理规则

- 内容运营内部规则问题可以独立 tracked 文档提交修正，不改变产品版本或 tag，也不触发部署。
- 只有公开内容对象、信息架构、页面投影、视觉/响应式或发布能力合同需要改变时，才由产品与视觉 task 评估并转入 `docs/iterations/current.md`。
- Engineering 只实现已经批准并进入当前迭代的问题，不顺手修复清单中的其他项。
- 内容提交只能包含目标 Observation 与必要 approved media，不夹带问题清单或规则修正。
- 关闭问题时保留原问题、修复事实和验证结果；不删除记录，不把完整 task 历史复制进来。

## 转入规则

- 只影响采集、审核、内容结构或既有发布命令的，留在本清单独立关闭。
- 影响公开内容对象、页面结构、视觉/响应式或发布能力合同的，保留本清单 ID，并转入 `docs/iterations/candidates/`；确认后才进入 `current.md`。
- 转入候选时，本清单只保留问题事实、证据和候选 ID；不得复制产品方案正文。产品 task 启动版本时只检查 `docs/iterations/candidates/`。
- 影响 Robotaxi 上游事实、系统状态或媒体审批的，回传 Robotaxi 责任 task；xingbuild 只记录证据边界和引用路径。
- 一个问题只能有一个 owner；跨 task 消息只传 ID、事实源、当前状态、阻断和下一动作。

## 已处理（近期）

### OPS-CONTENT-005：共享 main 与部署门禁使内容发布依赖产品工程时序

- 状态：已关闭
- 发现日期：2026-08-02
- 事实证据：`publish-content.command` 强制当前 checkout 为 clean `main`，并要求首次发布时 `origin/main == HEAD^`、同提交重试时 `origin/main == HEAD`；`scripts/content-scope-check.mjs` 复用同一门禁。内容提交 `6974b10` 后，远端被治理提交 `b02ee7a` 推进，原内容同 HEAD 重试按规则停止。
- 影响与风险：产品/Engineering 在共享 checkout 留下未提交文件时，内容不能发布；内容构建后主线前进时，内容必须临时换 clone 或重做基线。若放宽门禁，可能把旧构建或产品文件混入内容发布。
- 当前临时控制：内容 task 使用从最新 `origin/main` 刷新的干净隔离 clone，单 slug 检查、提交、push、部署和公网验收；不修改 `current.md`、产品版本/tag 或产品工程文件。
- 责任域 / 责任 task：xingbuild 内容发布能力；Engineering 负责命令与测试，内容 task 负责目标 slug；产品与视觉只确认公开发布能力是否变化。
- 是否需要产品版本：不进入任何产品版本；这是独立的内容发布能力修正。
- 根因与处理方案：不是内容判断或产品版本串行边界，而是共享 checkout 假设与缺少短时 release lease。方案为唯一干净内容 checkout、fetch→目标提交→push→build/deploy→verify 临界区租约，以及部署前再次确认远端仍为目标 HEAD。
- 关闭证据：`scripts/content-release.mjs` 从调用方 checkout 创建唯一干净内容 worktree，`scripts/lib/content-release-lease.mjs` 提供短时独占租约；主线前进时重建内容提交，部署前再次确认远端 HEAD。专项测试覆盖 lease 冲突/恢复、同 HEAD 重试、主线前进重建和远端漂移阻断。该修复不进入产品 current、产品版本或候选队列。

### OPS-CONTENT-006：隔离 worktree 未携带审核生命周期且 finalize 默认路径错误

- 状态：已确认
- 发现日期：2026-08-02
- 事实证据：真实运行 `./publish-content.command --slug waymo-london-autonomous-driving-specialist` 在从最新 `origin/main` 重建干净 worktree 后，`content:scope-check` 报 `Draft not found`；为让检查读取同一隔离审核目录设置 `XINGBUILD_CONTENT_ROOT` 后，push、build、Sites test 与 EdgeOne 均通过，但公网验收阶段报 `Cannot finalize <slug>: draft file is missing`。实际审核生命周期位于调用方隔离目录，`scripts/lib/content-finalize.mjs` 默认使用其 `projectRoot`，未跟随内容根目录。
- 影响与风险：能力在主线前进的真实场景中不能仅凭固定命令完成；若人工误删恢复材料，会失去失败重试与精确 finalize 的安全边界。该问题不影响已生成的公开内容事实，但使自动化闭环不完整。
- 当前临时控制：内容 task 使用同一隔离内容根目录完成检查；EdgeOne manifest 与目标 URL 对齐后，单独运行 `verify-content-release.mjs ... --finalize`，明确核验成功后再清理目标 draft/review/recovery；未生成重复提交。
- 责任域 / 责任 task：xingbuild 内容发布能力 / Engineering；内容及发布 task 负责提供真实运行证据。
- 是否需要产品版本：否；不改 UI、公开内容对象或产品版本/tag。
- 处理方案或转入路径：让发布 worktree显式携带目标 slug 的 draft/review/recovery，且 finalize 使用同一 `contentRoot`；补充真实 worktree + 主线前进 + 公网验收集成测试，验证无环境变量旁路即可完成并精确清理。
- 下一动作 / 恢复条件：Engineering确认修复合同并补充集成测试；在修复前保留上述临时控制，不把问题当作已自动闭环。
- 关闭验证：固定命令在干净隔离 worktree、主线前进和 CDN 传播延迟场景下，单条内容从 approve 到 finalize 全程成功，且无目标外 workspace 被修改。
